# 召回打分修复（批次60）：长文本被余弦系统性稀释

> 状态：**A 方案已落地**（λ=0.6）；B / C 未实施，保留为后续档位。
> 触发原因：批次59 把「批次59 决策」写进记忆库后，用该内容检索**检索不到自己**（只以「项目背景」身份出现）。
> 定位结论：不是写入问题、不是分词问题，而是**打分公式本身**——`forgetting.ts` 的 `scoreMemory` 中 `relevance` 用纯余弦，
> 余弦的分母含正文模长，**正文越长越吃亏**。

## 一、实测病根（真实账本 2911 条）

用 `node tools/eval-recall.mjs` 做 leave-one-out 自检索，λ=0（纯余弦，旧口径）：

| 策略 | Recall@5 | MRR@10 | 中位排名 | 短(<500) | 中(500-1500) | 长(>1500) |
|---|---|---|---|---|---|---|
| title（取首行标题作 query，20 字） | 10.1% | 0.082 | 384 | 23.2% | 1.9% | **0.0%（中位 1626）** |
| body（取正文中段作 query，20 字） | 12.6% | 0.076 | 246 | 23.2% | 5.8% | **4.7%（中位 560）** |
| title（40 字） | 23.2% | 0.150 | 224 | 46.3% | 13.5% | **1.6%（中位 986）** |
| body（60 字） | 37.4% | 0.239 | 20 | 64.6% | 36.5% | **3.1%（中位 273）** |

单条实例：新写入的 `mem_01M75JDPS14EVVN50KMEEPEMH1`（2094 字），query 的 13 个 token **全部命中（13/13 = 100%）**，
但纯余弦只有 **0.3823**，全库排名 **492 / 2911** → `top_k=5` 拿不到，只能退化成「项目背景」注入。

**结论：记忆写得越详细、越完整，越搜不到自己。** 这与「记忆库的价值 = 存得越细越有用」直接冲突。

## 二、评测方法（为什么可信 / 哪里不可信）

`tools/eval-recall.mjs`（只读，绝不写盘）：

- **口径用生产代码**：`import` 的是 `forgetting.ts` / `vector.ts`，不复制打分与分词，避免「评测口径与线上漂移」。
- **leave-one-out**：拿每条自己的内容派生 query，看它按 `hardFilter + scoreMemory` 排序后的名次。目标恒为「自己」，无需人工标注，也不会因标注偏好偏袒某方案。
- **等距抽样**：同一份账本每次抽到同一批样本，前后对比才可比（`--limit 200` 取 198 条有效）。
- **按正文长度分档**：这是「长文稀释」能否被修好的唯一直接证据。
- **覆盖率区分度诊断**（`--diagnose`）：目标覆盖率 vs 全员覆盖率。若两者几乎一样，说明覆盖率只是长度偏置的反向，A 方案的高分就是「词袋自我包含」的同义反复。

诊断实测（λ=0，200 条）：**目标覆盖率 0.959 / 全员均值 0.151 / p99 0.778 / 差值 0.807** → coverage 有强区分度，不是同义反复。

**必须承认的局限**：leave-one-out 的 query 取自本条目正文，**天然抬高覆盖率**（目标≈0.96，真实用户措辞通常到不了）。
所以它适合做「同一口径下的前后对比」，**不能当成绝对准确率**；也不能用它证明「λ 越大越好」（见下方 λ 选择）。

## 三、三方案对比

| | A · query 覆盖率融合 | B · 正文分块检索 | C · 长度归一化（BM25 式） |
|---|---|---|---|
| 核心做法 | `rel = cos^(1-λ) × coverage^λ`，coverage = query token 在正文里的命中比例 | 把正文切块（如 300–500 字/块），各自建向量，检索取**分段最高分** | 用 BM25 的长度归一化项重算词项权重，替换或校正余弦 |
| 修的是什么 | 用「提问概念被覆盖多少」对冲「正文太长导致余弦变小」 | 长文里只命中一个片段时，不再被整篇长度拖累 | 词频饱和 + 长度惩罚标准化，理论最完整 |
| 准确性 | 中（字面覆盖，不懂同义/改写） | 高（片段级定位最贴近「哪一句相关」） | 高（信息检索标准解法） |
| 改动面 | **小**：`forgetting.ts` 加 2 个纯函数 + `agent.ts` 接线 1 处 | **大**：存储结构、索引、向量数量 ×N、召回链路全改 | 中：要重算全库分数，历史排序普遍漂移 |
| 性能 | 每次召回多一次全量分词（实测 2911 条 ≈ 45ms） | 向量数 ×块数，存储与检索成本显著上升 | 与现状相当 |
| 风险 | λ 过大退化成词袋匹配，丢失语义能力 | 块边界切割语义、块间去重、迁移旧数据 | 排序整体漂移，需大范围重标定与回归 |
| 可回退 | **极好**：λ=0 逐字返回余弦（旧行为） | 差（要迁移数据） | 中（需保留旧分数字段） |

## 四、为什么先走 A

1. **改动最小、可一键回退**：λ=0 时 `fuseRelevance` **逐字返回**传入的余弦，等于旧口径（有专门用例锁住这条）。
2. **信号真实有效**：覆盖率区分度 0.807，不是长度偏置的另一种写法；且它与余弦互补——余弦看「整体像不像」，覆盖率看「提问的概念覆盖了多少」。
3. **能立刻验证**：有可复现基线，改完立刻能量化对比（见下表）。
4. B/C 成本高得多，且**若 A 已把问题压到可接受区间，就不必付那个代价**。

## 五、λ 选择（0.6，刻意不取饱和）

qlen=20、title 策略下的 λ 扫描：

| λ | 0 | 0.4 | 0.5 | 0.6 | 0.7 |
|---|---|---|---|---|---|
| 整体 Recall@5 | 10.1% | 65.7% | 69.7% | 76.3% | 84.3% |
| 短(<500) | 23.2% | 90.2% | 92.7% | 93.9% | 95.1% |
| 中(500-1500) | 1.9% | 76.9% | 84.6% | 88.5% | 94.2% |
| 长(>1500) | 0.0% | 25.0% | 28.1% | 43.8% | 62.5% |

数据上 λ 越大越好，但**不能再往上取**，原因：

- leave-one-out 的 query 取自本条目正文 → 覆盖率对目标≈1，**结构性地偏袒大 λ**；
- λ→1 时相关度退化成「词袋包含关系」，完全放弃语义——真实用户说「服务有点慢」而记忆写「P99 延迟」时，覆盖率≈0，会直接得 0 分；
- λ=0.6 保留 40% 余弦权重，是「修稀释」与「保语义」的折中。

**调参入口**：`src/core/memagent/forgetting.ts` 的 `RELEVANCE_FUSION_LAMBDA`。真实使用中若发现「明显相关的记忆搜不到」，先把 λ 降到 0.4–0.5 观察；若发现「总是召回只有字面重合、语义不相关的条目」，说明 λ 偏大。

## 七、诚实边界（写死，别当它已经被解决）

1. **A 是缓解，不是根治**。长文档仍明显低于短文档（43.8% vs 93.9%），因为余弦项还在按 `cos^0.4` 折算长度惩罚。要拉平必须走 **B（分块）**。
2. **不懂同义/改写**。覆盖率是字面 token 重合，与回显「命中片段高亮不做同义扩展」同一口径——宁可不标，也不猜。
3. **无共有词直接 0 分**，不制造假命中（有反向用例）。
4. **不改冷回填路径**：`sim≥0.85` 的兜底强信号仍是纯余弦判据，避免改动引入难以评估的行为漂移。
5. **性能随库规模线性增长**：2911 条约 45ms；到 2 万条量级应加正文 token 缓存（当前未加，避免缓存失效类 bug）。

## 八、什么时候升级到 B / C（决策规则）

按顺序判断，满足任一条就升级：

1. 长文档 Recall@5 长期低于 60%（当前 43.8%）→ **走 B**（分块检索，直接解决「长文只有一段相关」）。
2. 真实使用中出现「语义明显相关但一个词都不重合」的检索失败（如「慢」vs「延迟」）→ **走 C**（BM25 词项归一化）**或接向量模型**（纯字面方案无解）。
3. 库规模到 2 万条以上、召回延迟超过 200ms → 先加 token 缓存；仍不够再走 B（分块后可只检索候选块）。
4. 若 A 在真实使用中效果良好、长文档无投诉 → **停在 A**，不为了指标好看去付 B/C 的迁移成本。
