> 状态说明：`✅ 现有` = 已落地（MCP 或内核 API）；`🔲 缺口` = 预期但未实现（部分底层已具备，标注"底层已有"）；`🟡 未接线` = 引擎已实现但未接入内核 API。
>
> **〔批次43 对齐校正〕**：本文与 WorkBuddy 工作集 `multiagent-memory-ops` 对齐，**严格区分「Agent 面 MCP 工具」与「运维/管理端能力」两类计数口径**。Agent 面 = 12 个（读7 / 写2 / 管3）；运维/管理端能力（logs/overview/discover/sync/L0 授权族等）**单列不计入 Agent 工具数**。旧版把运维能力混进 Agent 面导致「≈17」的口径作废。

## 1. 出发点：记忆库的特性决定工具形态

本记忆库不是普通 CRUD 库，以下特性贯穿全部工具设计：

- **L0→L6 分层**：原始归档（L0 加密）→ 精炼产物（L1–L6），所以"写"只落 L0，"读"主要消费精炼层。
- **多租户三池 + 令牌作用域**：私人池 `P-<user>` 与共享池 `P-shared`、归档池 `P-archive`，所有读 / 管都受 `projectInScope` 约束（详见 `多用户三池隔离设计_D1-D25.md`）。〔**批次46-D6 已落地**〕三池按命名约定门禁（`classifyProject`：shared 恒可见 / archive 仅 admin / `P-<user>` 仅 owner 或 admin / 其余 general 按 `scope_project_ids`），账户由令牌库按令牌解析（D6-4）。
- **共享前必脱敏**：`P-shared` 只收脱敏后的 L1，脱敏闸门跑在内核。
- **衰减与遗忘**：记忆有半衰期 / decay，需要 GC 而非永久留存。
- **全量审计 + L0 保险库**：每次动作留痕，L0 原文受管理员密码与会话授权保护。

## 2. Agent 面 MCP 工具（12 个，读 7 / 写 2 / 管 3）

> `scope='session'` 诚实口径：内核 `sessionRecall()` 按 `session_id` 精确过滤（历史行无该字段一律不进视图，绝不拿 `created_at`/`project_id` 冒充），不做语义相关度计算故 `hit.score=0`，不注入项目背景；仍受 `projectInScope` 与 3000t 硬熔断约束，并写 `action='recall'` 审计（detail 带 `scope`/`session_id`）。
> `gc_report` 诚实口径（批次44-D5-3 落地、批次46-2/46-3/46-4 已接线）：46-4 起编排从 `ma.gc()` 切到 `ma.gcFull()`，报告按 D6 保留三项 `decayed`/`merged`/`conflicts_resolved` 不删不改名，并新增真实字段 `freshness_updated`/`scanned`/`migrated`/`summaries_created`/`summaries_filtered`/`merged_originals`/`compressed` 与 `conflict_resolution:{requested,verdict,resolved}` 回执；`compressed` 在 MCP 入口恒 0（未注入向量后端、仅清索引副本）。〔**批次46 已落地**〕「本系统无对应统计量」旧措辞已废止：六字段来自 `runForgettingCycle()` 真实事件、`scanned` 与 `freshness_updated` 同值；冲突裁决已由 46-3 下沉内核 `coreResolveConflict()`、46-4 经 `gc_report` 的 `resolve_conflicts`+`verdict` 暴露（二者都给才落定、绝不默认 `auto_override`）；`conflict_score`/`conflict_type` 内核无检测引擎故如实为 `null`（UI 显示「未检测」），不伪造。详见 [`specs/批次46-真正冲突裁决与摘要合并统计_落地方案.md`](批次46-真正冲突裁决与摘要合并统计_落地方案.md)。

## 5. 串起来的不变式

1. **写永远落 L0**：`write_memory` 只产生加密原始归档，绝不直写 `P-shared` / `P-<user>`；共享内容只能由「脱敏后的 L1」经 `routeL1` 晋升。
2. **读按令牌作用域**：`recall` / `list` / `manage` 统一 `projectInScope`（D6-2 三池：`P-shared` 恒可见 / `P-archive` 仅 admin / `P-<user>` 仅 owner 或 admin / general 按令牌 `scope_project_ids`），越界即拒。
3. **共享 = 已脱敏**：管线顺序（脱敏先于分流）保证 `P-shared` 里只有脱敏 L1。

---

## 6. 相对标准 CRUD 的三处不同（记忆库特性决定）

1. **写被强制降级为"只落 L0"**：标准库的写是直接 INSERT；这里 `write_memory` 只产生加密原始归档，精炼 / 脱敏 / 分流全交给内部管线。Agent 永远不能直写 `P-shared` / `P-<user>`。
2. **共享是派生量而非主数据**：`P-shared` 的内容只能由"脱敏后的 L1 经 `routeL1` 晋升"，所以"管理"里没有"直接写共享池"的工具——这是脱敏闸门的内核强制结果。
3. **遗忘是一等公民**：标准库忙着存，记忆库必须能"忘"（衰减 / GC / 归档 / 删除需确认），所以 `gc_report` 和 `manage_memory(delete/archive)` 是管理档的核心而非附属。

## 8. 待确认缺口

1. **跨项目检索 / 全局搜索（`scope='user+shared'`）**：当前 `recall_memory` 仅单 `project_id`。多用户下"搜我所有可见池"建议作为 `recall_memory` 的一个 `scope` 取值（非新工具），仍受 `projectInScope` 逐池校验（D21/D24）。
2. **导出 / 导入（backup / archive）**：多用户下归档 / 迁移需要，但属管理 / 运维能力，建议走独立管理员 CLI / REST（复用 `fileStorage` + `l0Split` / `l0Recovery`），并配套密钥环处理；不作为普通 Agent 令牌可触发的 MCP 工具（D25）。
