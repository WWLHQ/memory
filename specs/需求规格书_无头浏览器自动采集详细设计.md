# 无头浏览器自动采集详细设计（浏览器/页面不开也能导出网页对话）

> 配套：AGENTS.md §0 三道闸门、§0.1 纯净度、§0.2 交付闭环；`specs/code-map.md`；`specs/开发纪律_三道闸门.md`。
> 本文只做**设计**，不改运行时代码。所有接口/行号均来自现查源码（2026-11-18），非记忆推断。
> 目标：在**登录态有效期间**，无论用户浏览器开不开、对话页开不开，由 app 定时自动导出受支持站点的对话并入库；登录失效/风控/验证码时**显式记账并提示人工介入**，绝不静默假装成功。

---

## 0. 为什么插件做不到（问题定性，先钉死边界）

现查证据：

| 事实 | 出处 |
|---|---|
| 插件是 MV3，`background` = Service Worker | `browser-extension/webchat-exporter/manifest.json:27-29` |
| 调度靠 `chrome.alarms`（每 5 分钟巡检） | `background.js:26-27` |
| 内容从**已打开标签页的 DOM** 读取 | `background.js` 的 `exportOpenTabs`/`findSupportedTabs`（`chrome.tabs.query({})`）+ `content.js:53-79` 的 `readMessages` |
| 源码自己承认"页面关闭后扩展读不到页面内容，这是浏览器硬边界" | `background.js:21` |

**结论**：Service Worker 生命周期依附浏览器进程；浏览器关闭 → SW 不存在 → alarm 不触发；页面关闭 → 无 DOM → content script 读不到。这不是产品缺陷，是浏览器架构硬约束，**在插件内部无解**。

**唯一出路**：把"读 DOM"这件事的宿主从用户浏览器换成 **app 自己控制的无头浏览器**。插件可以保留（作为用户手动/前台导出的入口），但"无人值守自动采集"这条腿必须长在 app 侧。

## 1. 目标形态与诚实边界

### 1.1 能做到

- app 运行时（即使没有浏览器窗口、没有对话页），按配置周期自动唤起无头浏览器 → 打开站点 → 抽取 → 差分 → `POST /export` → 落盘入库。
- 每轮采集留账（站点、扫描数、导出数、失败原因），在 app UI 可见——**顺带打通上一轮"插件运行状态监控"需求**（见 §7）。
- 与 MV3 插件的关系（**2026-11-18 已拍板：阶段一无头为主、插件降级为手动入口**）：自动采集只走 app 侧无头定时器；插件保留 popup 手动"立即导出"、不建 `AUTO_ALARM`。双通道互为兜底（前提是 §1.3 共享签名账）整体降为**阶段二可选项**，见 §9.5.7。

### 1.2 做不到（必须对用户说清楚）

| 限制 | 原因 | 应对 |
|---|---|---|
| 登录态过期后无法自动续期 | 站点会话有时效，自动重登涉及凭据与风控 | 检测到登录页 → 标 `need_relogin` → 提示人工重登一次 |
| 验证码 | 无解，不应绕过 | 标 `blocked` → 提示人工 |
| 站点 DOM 改版导致选择器失效 | 选择器绑 DOM 结构 | 抽取返回空 + 诊断线索 → 显式告警，不静默 |
| 站点自动化检测/风控 | 无头浏览器有 webdriver 特征 | 真实 UA + persistent profile 缓解，**不承诺长期免疫** |
| 合规 | 自动化访问可能违反站点条款 | **用户自行拍板**，本设计不替用户做价值判断 |
| 反向兜底不稳（app 关→插件补） | app 关则 `/export` 接收端随之消亡，插件退回下载目录兜底；而 QQ 浏览器会把 `chat-exports/<站点>/` 子目录整个剥掉、文件甩进 `%TEMP%`（`webchatIngest.ts:2-8` 实录） | 兜底主方向只能是"浏览器关→无头补"；反向不承诺 |

> 定性：这是"登录有效期间的半自动"，不是"永动机"。文档全程按这个口径写，禁止实现成跑两天静默失败的假全自动。

### 1.3 双通道能否同时跑、能否相互兜底（2026-11-18 追加，现查结论）

> ⏸ **本节现为阶段二预案**：2026-11-18 用户已拍板走阶段一（单通道、插件不轮询），故本节所述竞态在本期不存在。保留全文，作为将来开双通道时的设计依据与准入判据（§9.5.7）。

**结论：进程与落盘层能共存；增量判定层会打架。要做成真兜底，必须先建"共享签名账"。**

| 层面 | 判定 | 现查依据 |
|---|---|---|
| 浏览器进程 | ✅ 能共存 | 插件跑用户浏览器、无头跑 app 自有 Chromium + 独立 userDataDir，两个进程互不占 profile 锁（§4.3 的独占锁只约束无头自己的 profile） |
| 落盘 | ✅ 能共存 | 两条链路都 `POST /export`，同令牌同目录；服务端 `pickPath` 按真实文件系统避让重名（`webchatIngest.ts:212`），不互相覆盖 |
| 增量判定 | ⚠️ **会重复入库** | 两链路各自维护签名（插件 `chrome.storage.local` v2 键 vs 无头 app config）→ 同段对话各写一份、时间戳不同故文件名不同 → 采集器哈希 `sha256(content\|src.name\|rel\|role)` **含文件名 rel**（`sessionCollector.ts:618,796-798`）→ 哈希不同 → 当成两条新记忆 |

**必须补的设计——共享签名账（shared signature ledger）**：

1. 位置：app 数据根 `webchat-auto-collect/signatures.json`，键 = `站点 + 会话路径`（与插件 `signatureKey = ...:siteKey:pathname` 口径对齐，`content.js:25-27`），值 = `core.signature(messages)`。
2. 写时机：**任一链路 `POST /export` 成功后**写签名（`onSaved` 之后写，沿用 0.4.0"投递失败不提前记签名"教训，`content.js:13-14`）。
3. 读时机：两条链路**导出前都先查**这张账——命中相同签名即跳过（记为 `no_new`），从源头上互斥。
4. 插件侧改造：把写/查签名接到 `POST /export` 的同一令牌通道（新增 `GET/POST /signature` 端点，或并入 `/status`），让 `chrome.storage.local` 的签名与 app 账同步——**否则插件仍按自己的旧账判定，与无头各写各的**。
5. 并发竞态：两链路可能同时通过"查账"再同时导出 → 服务端 `/export` 落盘成功回调里做一次"签名二次校验 + 原子写"，后到者判 `duplicate` 不记账（沿 `onSaved` 容错口径，失败不影响主流程）。

**原则援引**：本项目双通道既有约定是"主+补偿至少开一、主通道熔断自动降级、SHA-256 幂等不可关"（召回命中 [1][2]：`AC-003.6` / `T6 双通道配置`）；本案的教训是——**幂等键带路径时，跨路径的重复挡不住**，故必须把去重上移到"内容签名 + 共享账"层，而不能只依赖采集器的 per-file SHA-256。

### 1.4 插件与无头：二选一还是并存（2026-11-18 追加结论）

**结论：不是"必须同时"，推荐"无头为主、插件降级为手动入口"。分两阶段，不一步到位上双通道。**

> ✅ **2026-11-18 用户已拍板：采纳阶段一**（无头为主、插件降级为手动入口）。本文档此后的实现范围以阶段一为准；阶段二（共享签名账 P3.5）整体移出本期，见 §9.5.7。

| 维度 | 判定 |
|---|---|
| 自动能力覆盖 | 无头**能覆盖插件的全部自动导出场景**（浏览器开/不开都行），"自动"这一层插件可被完全替代 |
| 插件仅存的独特价值 | ① 用户正在聊天时点一下**立刻**导出当前对话（无头要等定时周期）；② app 未运行时的兜底（受 §1.2 反向兜底限制，不可靠） |
| 双开的代价 | 两条都保持"自动轮询"→ 重复入库（§1.3），必须付"共享签名账"成本 |

**两阶段落地**：

- **阶段一（默认，推荐）**：无头接管全部自动采集；**插件保留但关闭自动轮询**（`AUTO_ALARM` 不建），只保留"手动即时导出"按钮。此阶段**无重复入库问题**，不需要共享签名账，成本最低。
- **阶段二（可选）**：确需双通道互为兜底时，先完成 §9 的 P3.5（共享签名账），两条才允许同时自动跑。

> 硬约束：**在 P3.5 完成前，`AUTO_ALARM`（插件自动轮询）与无头采集定时器不得同时启用**，UI 必须二选一强制。违反即重复入库。

## 2. 架构与数据流

```
 [Electron 主进程]  常驻定时器（周期可配，默认保守 60min）
        │ 触发
        ▼
 [采集调度器 collectScheduler]  串行，单站点逐个跑
        │ launchPersistentContext(userDataDir)  ← 持久化登录态（首次有头登录）
        ▼
 [无头 Chromium]  page.goto(站点 URL)
        │ addScriptTag(shared/core.js) → page.evaluate(extractMessages)
        ▼
 [差分]  core.signature() 对上次签名 → 只取新增
        │
        ├─ 新增 → POST http://127.0.0.1:<port>/export （Bearer token）→ 服务端落盘 + onSaved 记账 → 采集器入库
        └─ 无新增/失败 → 写采集账（status/reason），不落盘
        │
        ▼
 [状态账 collect-ledger.jsonl]  → app UI「自动采集状态」页展示
```

复用现有链路的关键点：**不新造入库逻辑**。采集器把内容 POST 到已有 `webchatIngest` 的 `/export`，服务端生成文件名、Bearer 鉴权、`auditSource` 审计快照全部现成。

## 4. 关键接口（全部现查确认，不得臆造）

### 4.1 抽取内核（`shared/core.js`，冻结导出对象）

| 函数 | 签名/返回 | 用途 |
|---|---|---|
| `SITES` / `matchSite(url)` | 站点表 / 由 URL 匹配站点 | 判断当前页是否受支持 |
| `extractMessages(root, siteKey)` | `Message[]`（`{role, text}`） | 从 `document` 抽对话 |
| `signature(messages)` | string | 增量指纹 |
| `listSidebarItems(root, opts)` | 侧栏会话条目 | 历史会话遍历 |
| `findScrollAncestor(el)` / `describeSidebar(root)` | 滚动容器 / 结构诊断 | 虚拟列表滚动 + 选择器失效诊断 |
| `formatMarkdown(payload)` | string | 导出文档正文（与插件同格式） |

### 4.2 接收端（`src/electron/webchatIngest.ts`）

- 端点：`GET /ping`、`POST /export`、`POST /clear`（`:416/:462/:420`）。
- 鉴权：Bearer token，与端口一起写进插件目录 `runtime.json`（`:15`）。
- 安全口径：只监听 127.0.0.1；文件名服务端生成（`:16`）；站点段 `^[a-z0-9_-]{1,40}$`（`:31`）；body 上限 8MB（`:33`）。
- `onSaved` 回调签名：`({ site, path, bytes, at }) => void`（`:78`），成功落盘才触发。

**新增端点建议**：`POST /status`（复用同一 Bearer token 与 CORS 口径），接收采集账条目；GET 一个只读状态给 UI。失败不得影响 `/export` 主流程（沿用 `onSaved` 的 try/catch 容错写法，`:490-499`）。
**新增端点（双通道必需）**：`GET /signature?site=&path=` / `POST /signature`（同令牌），供插件与无头共用一张签名账（§1.3）。GET 查是否已有该签名，POST 由 `/export` 成功回调原子写入；两者都失败时退回各自本地签名（降级但不重复记账，账上标 `sig_degraded`）。

> ⏸ **本期不做（2026-11-18 拍板后）**：阶段一为单通道，`/signature` 整体移出本期，转阶段二入口条件（§9.5.7）。§1.3 的共享账设计作为阶段二预案保留，实现时**不要**顺手把它加进来。

### 4.3 浏览器启动方式（关键：**不能照搬 e2e**）

现查 `e2e/global-setup.mjs:140-152`：

```
spawn(chromium.executablePath(), ['--headless=new', '--remote-debugging-port=9222',
  '--no-sandbox','--disable-gpu','--disable-extensions', ...])
```

它**没有 `--user-data-dir`**（每次临时 profile，登录态不留存），且 `--disable-extensions`。E2E 用 `connectOverCDP` 是为了绕开本机 Windows 下 `browser.close()` 挂起（`harness.ts:1-3,69-77`）。

**本方案必须用持久化 profile，因此另起一套**：

- 用 `chromium.launchPersistentContext(userDataDir, { headless, args, executablePath })`，`userDataDir` 置于 app 数据根。
- 首次：以 `headless:false` 启动让用户登录各站点，登录成功后关闭；后续用**同一** `userDataDir` 以 `headless:true` 复用。
- 持久 context 由采集器长期持有，退出时释放并加超时兜底（借鉴 e2e 的 3s race，`harness.ts:73-76`），避免 `close()` 挂起。
- **同一时刻只允许一个进程持有该 userDataDir**（Chromium profile 独占锁），UI 上"重新登录"必须先停采集器再开有头窗口，文档与代码都要体现。

## 5. 数据结构

```ts
// 配置：app 数据根/webchat-auto-collect/config.json
interface AutoCollectConfig {
  enabled: boolean;
  intervalMinutes: number;        // 默认 60，保守；最小 15（防风控）
  headless: boolean;              // 首次登录后置 true
  userDataDir: string;            // 绝对目录，app 数据根下
  sites: Array<{
    siteKey: string;              // 与 core.SITES 一致
    url: string;                  // 对话页 URL（用户从浏览器复制）
    enabled: boolean;
  }>;
  maxHistoryPerRun: number;       // 单站单轮最多遍历会话数，防跑飞
}

// 采集账：collect-ledger.jsonl（追加式，跟 audit.jsonl 同风格）
interface CollectRunEntry {
  runId: string;                  // 随机 id
  startedAt: number;
  finishedAt: number;
  status: 'ok' | 'partial' | 'failed';
  sites: Array<{
    siteKey: string;
    status: 'exported' | 'no_new' | 'need_relogin' | 'blocked' | 'dom_changed' | 'error';
    scanned: number;
    exported: number;
    reason?: string;              // 人话，不塞原始 JSON（AGENTS.md §5 UI 铁律）
  }>;
}
```

> UI 展示一律中文名 + 一句摘要；`status` 枚举译成中文（如 `need_relogin` → "需要重新登录"），中文名单一来源，禁止把 `payload`/JSON 原文铺进界面（AGENTS.md §5）。

## 6. 采集主循环（伪代码，供实现对齐）

```
for each site in config.sites where enabled:
  result = { siteKey, status:'error', scanned:0, exported:0 }
  try:
    page = await ctx.newPage()
    await page.goto(site.url, { waitUntil:'domcontentloaded' })
    await page.addScriptTag({ path: coreJsPath })     // 注入 WebchatExporterCore
    // 登录态探测：URL 跳登录页 或 extractMessages 空且是登录页特征
    if (isLoginPage(page)) { result.status='need_relogin'; continue }
    const msgs = await page.evaluate(
      (k) => globalThis.WebchatExporterCore.extractMessages(document, k), site.siteKey)
    if (!msgs.length) { result.status='dom_changed'; result.reason=describeSidebar(page); continue }
    const sig = coreSignature(msgs)
    // 【阶段一】只比本地上次签名；阶段二才在此处加"先查共享账"，见 §9.5.7
    if (sig === lastSig(site.siteKey)) { result.status='no_new'; continue }
    const md = await page.evaluate((p) => WebchatExporterCore.formatMarkdown(p), payload)
    const saved = await postExport({ site:site.siteKey, title, url, markdown:md, auditSource:msgs }) // Bearer
    saveSig(site.siteKey, sig)        // 落盘成功后才记签名（沿用 0.4.0 教训，见 content.js:13-14）
    result.status='exported'; result.exported=1
  catch e:
    result.status='error'; result.reason=humanize(e)
  finally:
    appendLedger(result); await page.close()
```

**三条不可违背的纪律**（来自插件踩过的坑，现查注释佐证）：

1. **签名只在交付成功后写**（`content.js:13-14`：投递失败提前记签名会导致那段内容永远导不出）。
2. **一条站点失败不打断整轮**（`content.js:6-7`：逐条跳过带原因）。
3. **失败要留账可见**（`background.js:15-16`：0.3.0 就是因"完全静默"被用户投诉才加的账）。
4. ~~**双通道先查共享账再导出**~~（§1.3）：**阶段一不适用**（单通道无竞态）；阶段二恢复为：插件与无头谁先成功谁写签名，另一方读到即跳过；服务端 `/export` 成功回调再做一次原子二次校验，堵住"同时查账、同时导出"的竞态。

## 7. 与"状态监控"需求的合并（一鱼两吃）

上一轮问的"跑的情况能否传到 app 监控"与本案是同一件事的两面：

- **插件侧**：现状只有内容管道（`/export` `/clear` `/ping`），`lastAuto`/`tasks` 只存在 `chrome.storage.local`、只在弹窗可见（`background.js:1326` GET_STATUS）。要让 app 看到插件健康度，需插件每轮 `noteAutoRound` 后把状态摘要 `POST /status` 上报。
- **无头采集侧**：状态账本身就落在 app 数据根，天然可见。
- 两者共用同一个 `POST /status` 端点与同一套 UI 状态卡片，避免做两份。

UI 卡片字段（人话）：`最近检查时间` · `连续 N 轮无新增` · `本轮导出数` · `失败/需重登站点` · `一眼可见的重新登录入口`。

## 9.5 自动化落地路线图与详细实施方案（2026-11-18 追加）

### 9.5.0 核心命题：自动化 = 逐个消灭人工干预点

真正决定"能否少人工"的不是抓取算法，而是**全链路还剩几个人工干预点**。现查盘点如下（★ = 前几轮遗漏、最关键）：

| # | 人工干预点 | 现查事实 | 消除手段 | 消除后 |
|---|---|---|---|---|
| 1 | 开浏览器 + 开页面 + 点导出 | MV3 SW 随浏览器死、只读已开页 DOM（`background.js:21`） | 无头浏览器定时巡检（复用 `core.js`） | ✅ 全自动 |
| 2 | 每次登录输两遍密码 | 登录 scrypt、写解锁 PBKDF2，两套独立（`auth/hash.ts` / `crypto.ts:227`） | 登录那一次顺手解锁写密钥（方案A） | ✅ 全自动 |
| 3★ | 关掉 app 就停 | `window-all-closed` 非 macOS 直接 `app.quit()`（`main.ts:5206-5208`） | 托盘常驻，关窗只隐藏 | ⚠ 需新增 |
| 4★ | 重启电脑要手动开 app | 全库 `setLoginItemSettings` 零命中，无开机自启 | 开机自启 + 单实例（已有 `gotSingleInstanceLock`）+ 静默启动 | ⚠ 需新增 |
| 5 | 首次要给每个站点登录 | 无头需登录态 | `launchPersistentContext(userDataDir)` 持久化 | ✅ 仅一次 |
| 6 | 登录态过期 / 被登出 | 站点外部限制 | 探测 + 告警 + 一键重登，不静默 | ⚠ 人工一次（不可避免） |
| 7 | 验证码 / 风控 | 站点外部硬限制 | 无解，不应绕过 | ✗ 硬限制 |

**诚实结论**：零人工做不到；可保证的最优状态 = **一次设置（登录各站点）+ 日常零干预 + 登录失效时一次明确提醒**。

### 9.5.1 阶段 A：托盘常驻 + 开机自启（先做，最小改动最大收益）

**为什么排第一**：不做这层，采集器再自动也只在"app 恰好开着"时成立。

- **托盘常驻**
  - 新增 `Tray`（图标 + 菜单：显示主窗 / 暂停采集 / 立即采一轮 / 退出）。
  - 改 `window-all-closed`：非 macOS 不再 `app.quit()`，改为隐藏窗口、保留进程（保留退出快捷键与菜单里的"退出"真退）。
  - 采集定时器与托盘同生命周期：进程在 → 采集在。
- **开机自启**
  - `app.setLoginItemSettings({ openAtLogin: true, args: ['--hidden'] })`；提供 UI 开关（默认开）。
  - `--hidden` 启动时不建主窗，只建托盘 + 采集器。
  - 已有 `gotSingleInstanceLock`（`main.ts:5211` 引用），开机自启不会起多个实例；二次启动应唤醒已有实例而非新开。
- **验收（三道闸门）**：
  - B：关窗后进程仍在（托盘图标在）、定时器仍触发、任务管理器可见；重启系统后自动出现在托盘且不弹窗。
  - C：把"关窗隐藏"改回 `app.quit()` → 用例必须红灯（进程消失）；把 `openAtLogin` 置 false → 重启后不得自动出现。

### 9.5.2 阶段 B：无头采集器主循环（核心）

> 🚧 **落地前必须先改的口径（2026-11-18 现查，原方案用 Playwright 在打包态跑不起来）**
>
> | 现查事实 | 依据 | 后果 |
> |---|---|---|
> | `@playwright/test` 只在 `devDependencies` | `package.json` | 运行时不保证存在 |
> | 打包明确排除 node_modules | `electron-builder.config.cjs` 的 `files: ['!node_modules/**/*']` | 安装包里根本没有 playwright |
> | 主进程 bundle 只外置 3 个包 | `tools/build-electron.cjs`：`external: ['electron','pg','@electric-sql/pglite']` | `require('playwright')` 会被 esbuild 尝试内联或运行期报错 |
> | Playwright 还要自带浏览器二进制（150MB+） | 其发行模型 | 要么塞 extraResources（安装包暴涨），要么依赖系统 Chrome（版本/路径漂移） |
>
> **改为：用 Electron 自带的 Chromium。** 不引入任何新依赖、安装包不增大、也不必再担心 profile 撞 `Local State`：
>
> - 采集页 = `new BrowserWindow({ show:false, webPreferences:{ partition: 'persist:webchat-<site>' } })`；
>   持久登录态由 Electron 落在 `<userData>/Partitions/…`，与主进程自己的 `Local State` 天然隔离。
> - 注入 = 读 `shared/core.js` 源码 → `webContents.executeJavaScript(源码)`（等价于原方案的 `addScriptTag`），再 `executeJavaScript('WebchatExporterCore.extractMessages(document, k)')`。
> - `core.js` 路径复用现成解析器 `resolveWebchatExtensionDir`（`webchatExtensionPath.ts:13`，开发态读仓库、安装态读 `resources/webchat-exporter`）。
> - 首登：`show:true` 打开一次窗口让用户手动登录；日常 `show:false`。
> - 就绪判定：原方案用 `waitUntil:'domcontentloaded'`，改造后用 `did-finish-load` + 轮询「`extractMessages` 返回非空」（站点是 SPA，`did-finish-load` 早于消息渲染完成）。
> - **额外收益**：不是 CDP 注入，`navigator.webdriver` 不上报，风控面比 Playwright 更小。
> - **代价**：拿不到 Playwright 的 `waitForSelector` 等便利 API，等待逻辑要自己写（用轮询 + 上限超时，失败落 `dom_changed` 带 `describeSidebar` 诊断）。

- **模块**：`src/electron/webchatAutoCollect.ts`（调度 + 隐藏窗口封装）+ 复用 `shared/core.js`（不改）。
- **启动**：见上方改造口径（隐藏 `BrowserWindow` + `persist:` partition），**禁止照搬 `e2e/global-setup.mjs:140-152`**（临时 profile、禁扩展）。
- **单轮流程**：见 §6 主循环；关键三步不可省——成功后才写签名、单站失败不打断、失败必留账。
- **落盘**：`POST /export`（`webchatIngest.ts:462`），Bearer 鉴权；不新造入库逻辑。
- **验收**：§8 的 B1（浏览器全关仍导出）、B3（差分去重）、B4（单站失败不打断）。

#### 9.5.2.1 阶段 B 落地记录（2026-11-18 实现 / 2026-11-19 首轮真机实测修缺陷）

**首轮实测现象**（用户截图 + 动作日志）：DeepSeek 显示「页面结构变了 / 扫到 11 / 导出 0 / 诊断：(空)」，
`ipc:webchatAuto:run {"ms":26829}`。按 `AUTO_MAX_CHATS_PER_ROUND=3` 反推：3 条 × 8 秒超时 ≈ 24 秒 + 载入 ≈ 26.8 秒 → **三条全部等满超时，一条内容都没拿到**。

| # | 缺陷（都是代码缺陷，不是站点问题） | 真因 | 修法 |
|---|---|---|---|
| 1 | 「诊断：(空)」 | `core.describeSidebar()` 返回**对象**，驱动脚本按对象回传，但 `parseDriverResult` 用 `typeof === 'string'` 收 → 真结构被丢掉。旁证：插件 `content.js:208` 用的是 `probe.semantic/probe.groupRows` | 新增 `SidebarDiag` 结构类型 + `parseDiag()`；自由文本另走 `diagText`；`formatDiag()` 出人话 |
| 2 | 「跳了但没正文」与「压根没跳转」混成一个 0 | 驱动脚本只等「内容签名变化」，丢了插件里验证过的三态判定 | 移植 `content.js#waitForChange` 语义 → 每步记 `click-no-nav` / `nav-no-content` / 成功；失败原因进 `DriverStep` 与 UI 说明 |
| 3 | 抽不到就只能靠再打一版包去猜 | 无现场证据 | 一条都没抽到时落页面快照 `webchat-auto-collect/debug-<site>.html`（url/title/**visibility**/HTML，上限 300KB），动作日志同时落 `webchat-auto:steps` |

**配套口径变更**

- 手动「立即采一轮」上限提到 `AUTO_MAX_CHATS_MANUAL = 10`（定时轮仍 3）：11 条会话要连点 4 轮才看得完，体验上等于没修。
- `buildDriverScript` 增加可注入 `chatWaitMs`（默认 10s，最小 300ms）：既让手动轮能放宽，也让单测能用假 DOM **真跑**这段脚本——它是字符串，TypeScript 一眼都看不到，只做 `toContain` 断言等于没测。
- 隐藏窗口显式 `paintWhenInitiallyHidden: true`（BrowserWindow 选项，不是 `webPreferences` 里的）：隐藏窗口要走完整渲染管线，否则站点按「不可见」处理时正文永远不渲染。

#### 9.5.2.2 2026-11-19 第二次真机事故：登录页被当成会话列表，弹出 5 个外部窗口

**现象**：用户点「立即采一轮」后浏览器弹出 5 个窗口（DeepSeek 用户协议 ×2、工信部备案 ×2、飞书反馈表 ×1），
另有空白「MultiAgent Memory」窗口（`window.open` 从采集器弹出，主窗口标题其实是「MemoryDesk 记忆工作台」）。

**证据（现场，非推测）**
- `actions.log` 的 `webchat-auto:steps`：`忘记密码 / 立即注册 / 登录 / 验证码登录 / 使用 Apple 账号登录 / 用户协议 / 隐私政策 / 浙ICP备… / 联系我们 / 浙ICP备…` —— 10 次全点在登录页链接上。
- `webchat-auto-collect/debug-deepseek.html` 头：`url: https://chat.deepseek.com/forgot_password`、`visibility: visible`、体检 `语义条目 0 / 同类成组 18 / 正文区行 0`。
- 也就是说：隐藏窗口**根本没登录**，`listSidebarItems` 的「同类成组路」把登录表单按钮和页脚链接当成 18 条会话；第一次点「忘记密码」跳到找回密码页，之后继续点就打开了外链。

**三道防线（缺一不可）**
1. **登录页零点击**：`looksLikeLoginPage()` 同时看 URL 路径（`login/signin/register/forgot_password/...`）、表单元素（`input[type=password]` / 验证码容器）、正文文案（忘记密码 / 立即注册 / 验证码登录）；命中即 `needRelogin=true` 且 `limit=0`，**一条都不点**。判错最多少采一轮，点错就是替用户乱点外部网站。
2. **条目过滤**：在无头驱动侧过滤掉标签命中 `用户协议/隐私政策/备案/联系我们/Apple 账号…`、或最近锚点指向站外 / `target=_blank` 的条目。**不改 `core.js`**——它是插件真源，插件在真实登录态下工作正常；只收紧无头调用方。
3. **窗口硬护栏**：隐藏采集窗 `webContents.setWindowOpenHandler(() => ({action:'deny'}))`，任何漏网的 `window.open` 都开不出来，只记一条 `popup-denied` 审计。

**配套**：`judgeSite` 中 `needRelogin` 优先于一切（即使扫到 12 条也判 `need_relogin`，不再误报「页面结构变了」误导人去改选择器）；
`openLogin()` 先销毁旧的隐藏窗，保证用户登录后下一轮重建窗口、拿到新 cookie。
测试：`webchatAutoConfig.test.ts` 的「登录页一条都不点」「forgot_password URL」「外链/页脚过滤」「登录页优先判定」四例；变异「登录页继续点」→ 红。

**纪律**：`click-no-nav` 与 `nav-no-content` 是两种完全不同的故障（前者要换导航方式，后者要修抽取），**任何把它们合并成「失败了」的实现都视为缺陷**；`webchatAutoConfig.test.ts` 的「三态真跑」用例钉住这一点。

#### 9.5.2.3 2026-11-19 第三次真机实测：扫码不跳转 / 站点「使用环境异常」与 UA

**现象与判据**：登录窗截图停在「扫描成功 · 在微信中轻触允许即可登录」，说明扫码后仍等手机二次确认；
10:12:29 与 10:12:40 两次「立即采一轮」的结果都是 `need_relogin`（`ledger.jsonl`），证明**手机侧虽点了但会话并未建立**。
是否登录成功只看新一轮 `lastRound` 结果，不看窗口标题、不看截图上的绿色对勾。登录成功后**不需要关闭窗口来"提交"登录**——
站点自己 302 到会话页；关闭窗口只是收起 UI，cookie 已写入 `persist:webchat-deepseek` 分区（`D:\MultiAgent Memory\Partitions\...`），
下一轮隐藏窗复用同一分区即可。反之若结果仍 `need_relogin`，关窗也不会让登录生效。

**站点风险提示**：DeepSeek 前端检查 `navigator.userAgent` 含 `electron`，命中即弹「使用环境异常」。
现查同类内嵌实现（dsh-webview / dsh-webchat）一致做法：**只剥离 `Electron/x.y.z` token，其余 Chromium 指纹原样保留**；
不伪造完整 Chrome UA（版本指纹失配会加重 WAF 验证循环）。剥离后多数情况不再提示，但**不承诺永久免疫**——站点风控是外部硬限制（§1.2）。

**实现**：新增纯函数模块 `src/electron/webchatAutoUa.ts`（`stripElectronUa` / `applyCleanUserAgent`），
`webchatAutoCollect.ts` 的**隐藏采集窗与登录窗都在 `loadURL` 之前**调用一次。改动只发生在内核接线层，不动 `core.js`（插件真源）。
测试：`webchatAutoUa.test.ts` 5 例（含原样返回 / 大小写与多版本 / 不误伤普通单词 / 调用顺序）+
`webchatAutoCollect.ua.test.ts` 2 例（用假 `BrowserWindow` 真跑两类窗口的调用序列，断言 set-ua 早于 load）。

#### 9.5.2.4 2026-11-19 根因钉死：全局外链闸门把登录回调丢给了系统浏览器

**现象**：在 Electron 登录窗扫码、手机点「登录」后，页面跳转到 QQ浏览器（系统默认浏览器），Electron 窗永远停在「扫码成功 · 请在微信中轻触允许即可登录」。用户反复在 QQ浏览器 里登录成功，但采集器仍判 `need_relogin`。

**真正根因（源码现查）**：`main.ts` 的 `app.on('browser-window-created')` 给**每一个** BrowserWindow 挂了 `will-navigate` 闸门——
`isTrustedUrl(url)` 只认自家 `file:` 与本机 `http:` 源，**所有 https 导航**都会被 `event.preventDefault()` 并 `shell.openExternal(url)`。
DeepSeek 扫码确认后的回调是一次页面导航，于是被拦下、交给默认浏览器（QQ浏览器）；Electron 窗没收到回调，扫码态永久停留。
这与 cookie 隔离是两件事：即使回调留在 Electron，也仍需写入 `persist:webchat-deepseek` 分区；但**先被外链闸门截断**才是这次不跳转的直接原因。

**修复**：新增 `src/electron/webchatWindow.ts` 的 `isWebchatStoragePath()`（按 `session.storagePath` 匹配 `<userData>/Partitions/webchat-*`），
全局导航闸门只在**非**网页采集窗上挂载。采集窗与登录窗本来就该浏览外部站点，用自家窗口级护栏（隐藏窗 `setWindowOpenHandler: deny`）约束即可。
测试 4 例（含源码接线锁：闸门注册必须包在 `if (!isWebchatStoragePath(...))` 内）；两次变异红灯并还原：判据恒 false → 1 红；主进程去掉守卫 → 1 红。

### 9.5.3 阶段 C：登录时自动解锁写密钥（方案A，消除"输两遍"）

- **前提**：管理员为成员发一把 wrap，口令 = 该成员登录密码（`addMemberWriteWrap`，`l0vault.ts:526-535`；`passphrase` 由调用方指定，系统不强制，`main.ts:1498-1502`）。口令须 ≥`L0_MIN_SECRET_LEN`（`:528`）。
- **实现**：登录成功回调里（`useLoginMirror.ts:40-41` 已拿到 `sessionId`，`input.password` 在作用域内）调一次 `l0:writeUnlock(password, memberId=user_id, sessionId)`；走现成成员路径（`main.ts:1469-1477`，只校验 `ctx.user_id === memberId`）。
- **三条硬约束**：
  1. 解锁失败**绝不阻塞登录**——登录成功、写锁保持、UI 提示手动解锁；
  2. 明文密码用完即弃，不进日志/审计/URL；
  3. 改登录密码时须**同步重包**该成员 wrap，否则改密后写不了。
- **安全权衡（须用户拍板）**：口令直接等于登录密码 = 认证与加密同源，属安全降级。更稳的折中：口令 = `KDF(登录密码, 独立盐+userId)` 派生，用户仍只输一次但两把锁口令不同。
- **验收**：§8 增 B8——登录后 `writeUnlocked` 为 true（成员/管理员各一例）；wrap 缺失时登录成功但写锁保持 + 有提示；变异：去掉 `memberId` 校验 → 越权用例红灯。

### 9.5.4 阶段 D：入库层内容寻址去重（根治重复）

- **改动**：`sessionCollector.ts:796-798` 把哈希里的 `rel` 换成 `agentFor(src, rel)`（=站点标识，`:1114-1118`）：`sha256(content | 站点 | role)`。
- **效果**：同站点+同内容+同角色 = 同一指纹，无论几条链路、几个文件都只入一条；`webchatExportCollector.test.ts:249` 的"同内容不同站点视为两条"仍成立（站点进哈希）。

- **验收**：§8 的 B6（双开不重复）、变异 4/5（禁用查账/非原子二次校验必须红灯）。

### 2026-11-18 追加复盘（双通道共存问题）

- **现象与真根因**：问"两条链路能否同时跑相互兜底"。表层看是调度问题，真根因在**去重键的粒度**——采集器哈希 `sha256(content|src.name|rel|role)` 含文件名 `rel`（`sessionCollector.ts:796-798`），跨文件名的同内容重复挡不住。两链路各自维护签名、导出时间戳不同导致文件名不同，正好踩中这个粒度漏洞。
