## 0. 结论先行（本轮实测推翻了 D5-3 的一处记录）

1. **「本系统没有摘要类统计量」是不准确的**。目标契约 §7 的六个字段 `freshness_updated / migrated / summaries_created / summaries_filtered / merged_originals / compressed` 在 `src/core/memagent/forgetting.ts` 的 `ForgettingCycleReport` + `runForgettingCycle()` 里**早已完整实现且有真实事件来源**，由 `src/electron/main.ts` 每 6h 真实调度、写 `action='gc'` 审计，并有 `forgetting.test.ts` 覆盖。
2. 真正缺的不是统计量，而是**接线与隔离**：`runForgettingCycle()` 扫全库（`listMemories({})` 无 `project_id` 过滤）、无 `dry_run`、由主进程独立调度；`ma.gc()` → `coreGc()` 是另一条只做 `classifyLayer` 降档的路径。`gc_report(project_id, dry_run)` 走的是后者，所以只看到三项。
3. **冲突裁决在内核里是空的**：`GcReq.resolve_conflicts?: boolean` 已声明但 `coreGc` 从未读取；内核无 `ConflictRecord` / `Verdict` / `detect_conflicts`。真正的三模式裁决在**端壳层** `src/web/dispute/coreDispute.ts`，走 `ma._memoryOp`，且带三处硬编码/估算（`project_id:'P1'`、`conflict_score:0.8`、`conflict_type` 二选一）。
4. 因此本专项不是「从零造统计」，而是 **① 接线到已有遗忘周期引擎 ② 把三模式裁决下沉为内核原子 API ③ MCP 报告对齐 ④ 文档纠错**。
5. **红线**：`gc_report` 默认 `dry_run=true` 是只读报告；`auto_override` / `merge` 会归档旧记忆（准不可逆状态变更）。**不允许**把 `resolve_conflicts=true` 做成「自动覆盖开关」——必须与项目「delete 默认不开放 / 用户明确表态才动手 / 诚实降级」一致。

> **〔实施后解决说明 2026-11-05〕** 上段结论 ③ 与 §1 表 2/3/11 描述的「`coreGc` 未读 `resolve_conflicts` / 内核无裁决 API / MCP 明确拒绝」是 #17 立项时的实测现状，现已由 46-2（接线 `runForgettingCycle`）、46-3（新增 `conflict.ts` 内核裁决原子 API、端壳下沉去硬编码 P1/0.8）、46-4（MCP `gc_report` 放开 `resolve_conflicts`+`verdict`、报告改为 D6 分层十字段）**全部解决**。当前真实状态见 `需求规格书.md` §19.5 与 `mcpGcTools.ts`；本段与 §1 表保留为立项诊断史，不反映现状。

## 3. 三模式裁决语义（§9.7 + P7）与红线

### 3.1 已定稿的四值语义（内核原子能力）

| `Verdict` | 内核动作 | 写审计 | `conflicts_resolved` | 可逆性 |
|---|---|---|---|---|
| `auto_override` | 旧记忆 `archive`（`decay_class='archived'`，**不删正文**）；新记忆 `confidence = clamp(conf+0.1)`；两条 `conflict_id` 清空出队 | `action='conflict_resolve'`，detail 含 `old_id/new_id/verdict/conflict_id` 成对 | **+1** | 可逆（`restore` 可回温） |
| `merge` | 两条 `archive`；新建合并记忆（`content` 拼接后过 `checkL0ToL1Quality`，`merged_from=[old_id,new_id]`，`project_id` 取两条共同归属、不硬编码）；失败则整组回滚、保持 pending | `action='merge'` + `action='conflict_resolve'` | **+1**（仅成功时） | 可逆（原文保留） |
| `user_confirm` | **不改任何记忆状态**，保持 pending，提示用户确认 | `action='conflict_resolve'` + `detail.pending=true` | **+0** | — |
| `hold` | **不改任何记忆状态**，保持 pending | 同上 | **+0** | — |

### 3.2 冲突配对与数据完整性

- 配对来源只有两种**真实**数据：① 两条记忆共享非空 `conflict_id` 且均非 `archived/dormant/deleted`；② `action='conflict_resolve'` 审计中 `detail.pending=true` 且 old/new 两条记忆仍存在。**对手缺失 → 不入队、不伪造对**。
- `conflict_score` / `conflict_type`：内核目前**没有**检测引擎。定稿为「不伪造」——不输出分数、不猜测类型；若需要则如实回 `null` 并在 `note` 说明「§9.7 的 `detect_conflicts` 伪码未实现」。端壳 `coreDispute.ts:48` 的硬编码 0.8 在 46-3 下沉时一并移除。
- `project_id`：两条必须同项目且落在令牌作用域内；跨项目 / 越界一律拒绝并写明原因。
- `locked` 记忆：沿用 G4「仅 `unlock` 放行」，冲突裁决触碰 locked 行时回 `blocked_locked:true` 且不计入 resolved。

### 3.3 红线（不得突破）

1. **`resolve_conflicts` 不是自动覆盖开关**。它只能表示「本次执行用户已显式选定的裁决」；未指定 `verdict` 时只做 dry-run 演算或明确拒绝，**绝不默认 `auto_override`**。
2. **`dry_run=true` 全程零写入**：不 `putMemory`、不 `appendAudit`、不 `vector.upsert/remove`、不 `ma.write`，`audit=null`（沿用 D5-3 口径）。
3. 裁决**不删除**任何记忆（`archive` 可 `restore`），不触碰 L0 密文，不回显 `content_l0_enc` / `content_orig` / `has_l0`。
4. `conflicts_resolved` 只数**本周期内真实落定**的冲突对；历史 `conflict_resolve` 审计不得回放计数（防止同一冲突被反复计入）。
5. 单次裁决必须写**成对审计**（`old_id` + `new_id`），符合 §18.4 约束 5。
