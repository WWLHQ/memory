# 管理员与成员权限设计（按实际应用场景重新设计）

> 本文是**设计稿**，不含代码改动。设计输入为系统当前的真实运行形态与既有代码事实，不采用对话中临时提出的角色约束。
> 所有现状结论均标注 `[文件:行号]`，便于复核；未标注者为设计主张。

## 0. 设计前提：这套系统实际是怎么被用的

| 场景事实 | 证据 |
|---|---|
| 本地优先的 Electron 桌面应用，数据与审计全部落本机，无云依赖 | `AGENTS.md` §1 |
| 角色只有两个：`admin`（系统最高权限：账号/团队/安全策略/数据位置）、`member`（普通用户） | `src/types/home.ts:10-11` |
| 角色唯一判定入口 `isAdminContext()`，缺省按 member 处理 | `src/types/home.ts:27-30` |
| 内置管理员账号 `admin` 是**开箱默认账号**；本机当前只有 2 个账号 | `src/auth/loginService.ts:16`；`%APPDATA%/MultiAgent Memory/home-accounts.json` |
| MCP 是**机器级单令牌**，一个值同时喂 8202/8204/8203 与接入面板；按客户端/成员发独立密钥属 45-B，**未实现** | `specs/需求规格书.md:4278`；`specs/MANUAL-TEST-FIX-BATCH-26B.md:38` |
| 采集器是**后台自动行为**（首扫 + 定时轮询 + 退避），不由任何登录角色驱动 | `src/electron/main.ts:3202-3210`、`3966`、`4001` |
| `tenant.json` 是机器级身份单一真源，被 MCP 引导账户、采集器、webhook、同步中枢共用 | `src/electron/main.ts:2791`、`3080`、`3125`、`3184`、`3265`、`2821` |
| 规格红线 R1：租户 ID 仅全局注入，前端禁手填 | `specs/需求规格书_Agent接入页字段级交互规格.md:131,144` |
| 现有门禁只有 `requireAdmin` / `requireSession` 两类；`requireDataPlaneSession` 是 `requireSession` 的数据面适配层，非第三套判定 | `src/electron/main.ts:842`、`2252` |
| 会话 TTL 12h；角色/团队变更立即吊销该用户全部会话 | `src/home/server.ts:340`、`755`、`763` |

**推导出的四条场景分层**：

- **S1 安装态**：首启向导 `setup.html` 选数据目录、设 L0 管理密码、导恢复卡、确定本机身份。此时**无会话、无角色**，主体是"本机属主"这一物理事实，不是账号。
- **S2 日常使用态**：写/召回记忆、个人记忆收件箱、触发一次采集、Agent 接入与使用、被授权后查阅 L0 原文。主体是**成员**，也是产品的核心价值所在。
- **S3 运维/安全态**：账号与角色、团队分配、L0 密钥与授权审批、模型/网关参数、召回与补炼策略、备份与数据位置、账本维护。主体是**管理员**。
- **S4 系统态**：采集器定时扫描、MCP 服务、webhook、同步中枢、密钥环轮换。**不属于任何登录角色**，由进程持机器级凭据运行。

## 1. 核心设计主张

### 1.1 管理员 = 成员的超集，不采用硬互斥

`admin` 在仓库定义里就是"系统最高权限"（`src/types/home.ts:10`），且是开箱默认账号。若把数据面、采集、Agent 会话对 admin 硬禁，**用户装完用默认账号登录将既写不进记忆、也召回不到任何东西**——这直接破坏 S2，属于设计事故。

因此采用**能力叠加 + 强审计**实现职责分离，而不是角色互斥：

| 手段 | 说明 |
|---|---|
| 能力叠加 | admin 拥有 member 的全部能力，外加 S3 管理域独占能力 |
| 破坏性门槛 | 清空账本、重建/拆分 L0、删除记忆、写审计等仍要求 admin（现状即如此，不反转） |
| 强制留痕 | admin 调用任何"数据面读/写"通道时，审计记录带 `actor_role=admin` 与 `via=admin_override`，可检索、不可关闭 |
| 视图分离 | admin 登录后默认落"管理台"视图；数据功能可用但需显式切换，UI 不做隐藏、也不做假禁用（**2026-11-15 已确认新增，规格见 §14.1**） |
| 最小读 | 管理台卡片只展示计数/状态/健康度，不铺陈记忆正文；正文查看必须跳转到数据页并留痕 |

### 1.2 四个域，按"谁承担后果"划线

| 域 | 归属 | 判据 |
|---|---|---|
| **身份域** `tenant.json` | S1 安装态写入 + S3 管理员维护；成员只读 | 改它影响**全库、所有账号、MCP 引导账户、存量记忆的租户口径**，属于安装级事实，不是个人资料 |
| **参数/安全域** | 管理员独占写；成员只读 | 改的是系统行为与凭据，普通使用者无需承担后果 |
| **数据/使用域** | 成员可用；管理员超集可用（强制留痕） | 记忆内容的生产与消费 |
| **系统域** | 无角色 | 后台任务与机器凭据 |

### 1.3 凭据与角色解耦

MCP 引导令牌是机器级凭据（`需求规格书.md:4278`），其 `is_admin=true` 表示**令牌能力等级**，不是"管理员这个人在操作"。在 45-B 落地"每成员独立密钥"之前，不要把令牌的 admin 语义与登录角色混为一谈；权限矩阵里单列"系统域"。

## 2. 门禁模型

保留现有两个门禁，新增一个"数据使用"门禁；**不新增 `requireMember`**（超集模型不需要"仅成员"）。

| 门禁 | 判定 | 拒绝码 | 适用 |
|---|---|---|---|
| `requireSession` | 会话有效 | `E_AUTH_SESSION` | 中性只读（状态、配置读取） |
| `requireAdmin` | 会话有效且 `role === 'admin'` | `E_AUTH_FORBIDDEN` | S3 参数/安全/破坏性动作 |
| `requireDataUse`（新增） | 会话有效；`admin` 或 `member` 均放行；`role === 'admin'` 时打审计标记 | `E_AUTH_SESSION` | 数据面读写、采集触发、Agent 会话 |
| 无鉴权 | — | — | 仅限 `l0:writeUnlocked` 这类进程级布尔状态 |

设计约束：

1. 会话真源恒为 `homeServerRef.getSessionContext(sid)`，**不接受渲染层自报角色**（沿用 `main.ts:842-854`）。
2. `requireDataUse` 的审计标记走 `actionLog('ipc', channel, { actor_role, via: 'admin_override' })`，只读调用也记；不得由调用方传参覆盖。
3. **按实际场景收缩（2026-11-15 定稿）**：需要补会话校验的裸奔通道只有 `collector:triggerNow`、`hostAgentDetect:config` 两处；`collector:status`（状态栏/监控页登录前可观测）与 `mcp:clients`（提交 `cf24de5` 有意改为登录前可见）**保持免登录**，不做升级。
4. 拒绝时统一返回结构化结果，不抛裸异常给渲染层。
5. 角色变更后旧会话已由 `revokeSessionsOfUser` 吊销（`server.ts:755`），门禁无需重复处理。

## 3. 管理员权限清单（目标态）

### 3.1 独占能力（成员一律拒绝）

| 组 | 通道 / 端点 | 现状 |
|---|---|---|
| 账号与组织 | `/api/accounts`、`/api/accounts/update`（role、team_id）、`/api/keys/*`（mint/revoke/list） | 已 admin（`server.ts:727-801`） |
| 安全策略 | 密码策略 POST、`dataRoot:change/restoreDefault`、`backup:saveConfig` | 已 admin |
| L0 密钥与授权**配置** | `l0:status/setup/changePassword/listRequests/listGrants/grant/deny/revoke/writeLock/addMemberWriteWrap/removeMemberWriteWrap/migrate/splitRun/rebuildRun/recovery*`、无 grant_id 的 `l0:unlock` | 已 admin（`main.ts:1329-1762`） |
| 模型与网关参数 | `llm:configSet/test/billingKey` | 已 admin |
| 召回与精炼策略 | `recallHard:set`、`refine:setEnabled/setCap` | 已 admin |
| 全库运维动作（**非参数配置**，释义见 §14.3） | `ledger:resetRecollect`、`rules:rejudgeRun`、`refine:backfill/retryFailed`、`backup:runNow` | 已 admin |
| 身份维护 | `tenant:set`（新）、`tenant:normalize`（新，复用 45-A2 备份闸门）、`tenant:read`（新，只读） | 无写口，需新增 |
| MCP 接入凭据 | `mcp:clientSnippet/clientWire`（下发令牌写客户端配置） | 已 admin，保持（凭据类，不按数据活动移交） |

### 3.2 继承能力（与成员相同，但强制留痕）

`storage:*` 全部、`/api/kernel/invoke`、`queryAudit`、`personal:invoke`、`collector:triggerNow`、`hostScan:run`、`hostAgentDetect:run/config`、`l0:request`、`l0:unlock`(带 grant_id)、`l0:writeUnlock`(memberId 分支)、`l0:myWriteWrap`、`l0:decrypt/seal/blobs/heartbeat/lock/sessionInfo`。`collector:status` 与 `mcp:clients` 保持免登录（登录前可观测），不在本列。

### 3.3 管理员明确不做的事

- 不通过管理台卡片直接展示记忆正文（只给计数与状态）。
- 不因角色自动获得他人 L0 原文的免授权查阅（查阅仍走 grant 流程，管理员路径仅指"管理密码直接查阅"这一既有能力，且必须留痕）。
- 不把 `is_admin` 令牌能力等同于管理员本人操作。

## 4. 成员权限清单（目标态）

| 组 | 能力 | 门禁 |
|---|---|---|
| 记忆 | 写/读/列/查重、召回、个人记忆收件箱、查询审计 | `requireDataUse` |
| 删除与审计写 | `deleteMemory`、`appendAudit` —— **维持 admin 专属不变**（`server.ts:127`），成员仍需管理员执行 | `requireAdmin` |
| 采集 | 触发一次采集、查看采集状态、宿主扫描、Agent 发现与配置 | `requireDataUse`（现裸奔，补门禁） |
| Agent 接入 | 查看已接入客户端 `mcp:clients`（免登录可见，登录前也可观测）、一键开关 `mcp:clientEnable`（需登录） | 一键接入/片段/写入令牌归管理员 |
| 身份 | `tenant:get` 只读；可在 UI 看到三元组及中文释义 | `requireSession` |
| L0 使用 | 申请查阅 `l0:request`、用 grant_id + 一次性密码查阅 `l0:unlock`、用自己的口令自解锁写密钥 `l0:writeUnlock`(memberId)、查自己的写包 `l0:myWriteWrap`、会话内 `decrypt/seal/blobs/heartbeat/lock/sessionInfo` | `requireSession` + 本人归属校验 |
| 只读配置 | 备份配置、LLM 配置状态、召回开关状态、精炼状态 | `requireSession` |

**成员明确禁止**：账号/角色/团队管理、API 密钥签发、L0 授权审批与密钥配置、参数写入、`tenant.json` 写入、令牌下发、账本破坏性维护。

## 5. 公共 / 系统通道（不参与角色矩阵）

| 通道 | 理由 |
|---|---|
| `l0:writeUnlocked` | 进程级布尔事实，无账号私密信息；加会话会让首页恒显"未解锁"（`main.ts:1403-1407` 已写明根因） |
| `setup:*` 首启向导 | 无会话、无角色，门禁换成"本机此刻还没有需要保护的东西"（`main.ts:2345-2357`） |
| 采集器定时扫描、webhook、同步中枢、MCP 服务 | S4 系统态，进程持机器级凭据运行 |

## 6. 专项设计

### 6.1 `tenant.json`（数据身份三元组）

**归属**：S1 首启向导首次落盘（`loadOrCreateTenant` 首建 `DEFAULT_TENANT = u1/t1/e1`，`src/shared/tenantDefaults.ts:13`）；S3 管理员在安全页维护；成员只读。理由见 §1.2，且规格 R1 明确禁前端手填租户 ID。

**新增写入口**（当前 `tenantSource.ts` 只有 `loadOrCreateTenant`，无写函数）：

- `writeTenant(dataRoot, next)`：先用 `normalizeTenantTriple` 校验三字段非空 → 备份原文件（复用 `backupBeforeKernelChange` 口径）→ 原子写 + 0600 → 返回新旧值。
- `tenant:set`（`requireAdmin`）：入参只接受三元组，不接受渲染层自报的其他字段。
- `tenant:read`（新增，`requireSession`）：只读回显 `tenant.json` 三元组。**不得复用 `tenant:get`** —— 后者返回的是登录会话三元组（`main.ts:2335-2341` 取 `gate.ctx.*`），与机器级 `tenant.json` 是两套值（本机当前会话侧 `local / admin-team`，内核侧 `u1 / t1 / e1`）；混用会让管理员「看到的」和「编辑的」不是同一份，属设计缺陷，须在实现时避免。

**护栏（缺一不可）**：

1. 页面明示「修改影响所有账号、所有历史记忆、MCP 与同步口径」。
2. 二次确认（输入 `TENANT`）；写前备份成功才允许写。
3. 写 `actions.log`：`app:tenant-set`，含旧/新三元组、操作者、`request_id`；不记任何密钥。
4. **重启生效**：`tenantTriple` 是启动期一次性快照（`main.ts:2791`），页面必须显示"已保存，重启后生效"，不得谎称即时生效。
5. 重启时若检测到三元组变化，按 45-A2 口径预览存量行差异并提示执行归一（`main.ts:2845-2860`），**不自动改写用户账本**。
6. 变更 `user_id` 会使 `MAM_PERSONAL_OWNER_BINDINGS` 中的 `kernel_user_id` 失配，页面需给出诚实提示。

### 6.2 采集与 Agent 会话

按动作性质切，不按角色一刀切：

| 动作 | 域 | 归属 |
|---|---|---|
| 后台定时采集、首扫、退避 | S4 系统态 | 进程，无角色 |
| 触发一次采集 / 查看状态 / 宿主扫描 / Agent 发现 | S2 使用 | `requireDataUse`（成员与管理员均可用） |
| 采集策略、开关、白名单、周期 | S3 参数 | 管理员（当前策略多为代码常量，未来若做成配置项，归管理员） |
| 生成客户端配置片段、写入 MCP 令牌 | S3 凭据 | 管理员 |
| 查看已接入客户端、一键接入流程 | S2 使用 | `requireDataUse` |

补充（按实际场景收缩后）：`collector:triggerNow` 与 `hostAgentDetect:config` 此前**无会话门禁**，本设计把它们纳入 `requireDataUse`，这是安全修复而非角色调整；`collector:status`、`mcp:clients` 保持免登录（登录前可观测是有意决策，见 §2 约束 3）。

### 6.3 L0 授权：配置与使用分离

| 类别 | 通道 | 归属 |
|---|---|---|
| 配置 | 设/改管理密码、发放/撤销成员写包、审批/驳回/撤销查阅授权、查看请求与授权清单、写锁、迁移、拆分、重建、恢复码、管理密码直接查阅 | 管理员独占 |
| 使用 | 申请授权、用 grant_id + 一次性密码查阅、自解锁自己的写密钥、查自己的写包、会话内解密/密封/心跳/关闭 | 成员（管理员超集） |

**必须保住"使用"侧**：成员若不能自解锁写密钥（`main.ts:1386-1394`），写入会持续撞 `E_L0_LOCKED`，产品不可用。这与"成员禁止配置"不冲突——成员改不了任何授权参数，只是消费已发放给自己的授权。

### 6.4 MCP 令牌域

保持机器级单令牌现状，`is_admin=true` 仅表示令牌能力，**不映射到登录角色**。将来 45-B 落地"每成员独立密钥"后，再把密钥绑定到 `Member` 并在此矩阵新增"密钥作用域"列。在此之前，禁止把 `create_project` / `mint_token` 的 admin 门禁解释成"管理员本人操作"（`src/core/memagent/mcpProjectTools.ts:43,114`）。

## 8. 审计与可观测

- 所有 `requireAdmin` 拒绝沿用现有 `denied: 'not_admin'` 留痕（`main.ts:850`）。
- 新增 `requireDataUse` 的 `actor_role=admin` 标记，写入 `actions.log`；只读调用也记。
- `tenant:set` 单独动作名，含新旧值与 `request_id`；不记密钥、不记恢复码。
- 审计账本本身（`audit.jsonl`）保持只增不减；管理台只给聚合计数，不提供批量删除入口。

### 14.3 `backup:runNow` / `refine:backfill` 释义与归属

#### `backup:runNow`（UI 文案「立即备份」，`src/web/Home/programLogLabels.ts:139`）

`main.ts:913-918`：`requireAdmin` → 写 `backup:manual-requested` → `runBackupOnce('manual')`。`runBackupOnce`（`main.ts:731-774`）做的是：

1. `planBackupFiles` 列出**记忆库 `memories.db.json` + L0 原数据库 `memories.l0.json` + 密钥环 + 审计账本 `audit.jsonl`**（批次37-D 双库、41-A 加审计），缺哪个如实报缺，不会只备一个库就说"已备份"；
2. 逐文件 `copyFile` 到配置目录（目录由 `backupSaveConfig` 校验：绝对路径 / 拒 UNC / 可写，`main.ts:859-887`）；
3. **每份复制后调 `rotateBackups(dir, prefix, cfg.keepCount)` 按保留份数滚动删除旧备份**（`main.ts:751`；`871` 注释明确「配错目录会让滚动删除在共享目录里误删别人的同名文件」）；
4. 写一条 `memory_op` 审计（`op:'auto_backup'`，`trigger=manual`，带文件清单 / 目录 / keep / 记忆条数），回执逐文件说明备了什么。

→ 它是「**读全库 → 复制到外部目录 → 删旧备份 → 写审计**」的一次性运维执行动作，**不是参数配置**，且带删除副作用。

#### `refine:backfill`（UI 文案「把存量行入队补炼」，`programLogLabels.ts:190`）

`main.ts:1983-1992`：`requireAdmin` → `enqueueRows(loadRefineQueue(...), await storage.listMemories({}))` → 保存队列 → 记 `refine:backfill-run`。`enqueueRows`（`refineQueue.ts:166-192`）遍历全库，跳过 `pinned` / `locked` / 已删 / 无 L1 / 已有深层的行，把「有 L1 但没有 L2–L6 深层正文」的历史行标成 `pending`；只增不改、幂等。之后 `runRefineTick`（`main.ts:1846-1875`）定时取一条，**调 LLM 网关生成 L2–L6 深层并写回记忆与向量**，受 `cap_rows` 每日额度限制、`llm_calls` 计费。启动时 `startRefineQueue`（`main.ts:1877-1892`）本就会自动跑一次同样的全量入队，手动按钮等于再跑一遍。

→ 它是「**给全库历史记忆批量排 LLM 补炼的活**」，本身不改正文，但后果是持续消耗 LLM 额度 / 费用并改写记忆深层结构，**不是参数配置**。

#### 归属（已定）

**用户 2026-11-15 15:11 确认**：两者都不算「参数配置」，归 **S3 全库运维动作 · 管理员独占**，成员禁止。判据是 §1.2 的「谁承担后果」：作用范围是整库而非个人、带外部副作用（删文件 / 烧钱 / 改写深层）、需承担审计责任。§3.1 的分组名已由「账本破坏性维护」改为「全库运维动作（非参数配置）」，**现状门禁不变**（两者现在就已是 `requireAdmin`），因此这一项只影响文档措辞与后续新增动作的分类，不产生代码改动。
