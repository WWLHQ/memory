## 一、云端同步（建议 42-A..42-D）

核心逻辑**已写好且已测**，差的是「接线 + 中枢落地 + 冲突裁决 UI」。

**前置拍板（必须先定，否则 42-A 无从下手）**
1. 中枢落地形态：`PgSyncHub` 是**进程内 pglite**（传 `dataDir` 落单机文件），**不是远程 Postgres**——若真要「多机共享中枢」，得先决定换成远端 PG / 或接受「单机 pglite 文件」作为跨端（桌面 + Web + CLI 同机）中枢。这是本项的第一道分叉口。
2. 桌面主源 + 自动 LWW 的「语义互斥进 §9.7 队列」：多端真并发时**要不要人工裁决 UI**，还是先全自动 LWW、裁决 UI 后补。

**拆分建议**
- **42-A 内核 `sync()` 接真**：`agent.ts` 的 `sync()` 从 `E_NOT_IMPLEMENTED` 换成真调 `syncUp`/`syncDown`（调用方注入 `PgSyncHub` + 本端 store）。先跑通「上行 sha256 幂等 + 下行 since 增量」；`hub` 未注入时**保留**如实报未接线，不删、不假装。
- **42-B 端壳中枢 + IPC**：`main.ts` 实例化持久化 `PgSyncHub`（`dataDir` = 数据根下 `sync-hub/`，随迁移白名单走）、新增 `sync:*` IPC（上行/下行需会话，中枢配置需管理员）、`preload.ts`/`hostBridge.ts` 接线。
- **42-C 三端引擎 + §9.7 冲突裁决 UI**：`syncUp`/`syncDown` 真跑桌面/Web/CLI；冲突队列出「人工裁决」页（列 pending 冲突、选胜者、落 `conflict_resolve` 审计）。
- **42-D 备份与迁移收口**：`sync-hub/` 持久化文件进 `DATA_ROOT_MIGRATE_FILES` + `backups/`（新前缀），口径对齐批次41-A 的审计四源备份。

## 二、每日全量补齐（建议 43-A，依赖 42）

- **43-A §3.4 定时 `reconcile`**：新增「每日全量对账」调度（缺省每日一次，env 可调、缺省值定死），跑 `reconcile(hub, local, {team_id})`——补本地缺的行 + 指纹校验，结果落 `sync_reconcile` 审计 + 动作日志。**只补本地没有的行，不改已有行**：指纹不一致的行进 `integrity_issues` 如实报，**不静默覆盖**（与「删除不可逆、备份是唯一退路」同口径）。
- 边界：依赖 42-A/42-B 的中枢已接线；**中枢未接线时本项无意义**（没有远端可对账），不伪造对账回执。

## 三、独立采集守护进程（建议 44-A..44-B，风险最高）

- **44-A 采集抽成无头常驻**：把「采集 + L0→L1 质量门 + 入队补炼」从 `main.ts` 抽成可 headless 常驻的模块（如 `node tools/collect-daemon`），**不依赖 Electron 窗口**；桌面端没开也能继续按 Agent 会话日志增量采集。
- **44-B 双写者锁协同**：守护常驻 + 桌面端偶发 = **两个潜在写者**，必须定死批次28-A 建议性写锁的口径（谁持写锁、谁降级只读镜像、锁竞争时如何不误删/双写）。这是本项最危险处。
- 边界：架构改动最大（新增常驻进程 + 进程间锁），**建议排在 42/43 之后**，且需单独实机走查（多进程持锁实机难覆盖，属 E2E/实机口径）。
