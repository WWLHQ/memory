## 0. 一句话结论

**真跑了模型之后，P1-6 达不到生产化门槛。** 384 维语义向量在这个打分管线里最好只带来 **R@1 +2.3pp / NDCG@5 +0.013**（混合变体），纯 e5 替换直接崩塌（R@1=0%）；代价却是安装包 124MB→约 380MB（本机 CPU 不支持 AVX512-VNNI，只能用 235MB 的 O4 fp32）、全库重嵌入 **544.9 秒（9.1 分钟）**、冷加载 1.7 秒。**建议：P1-6 生产化暂缓，保留本评估作为决策依据；P1-7 继续暂缓。**

## 1. 评估设计（可复核）

### 1.1 两套口径，互不冒充

| 口径 | 数据 | 真值 | 作用 |
|---|---|---|---|
| ① LOO 客观排名 | 从 5663 条候选中等距抽 300 条，query = 该条正文首行（与 `tools/eval-recall.mjs` 同口径），目标 = 来源条目自己 | 目标恒为自己，无需人工标注 | **质量主判据** |
| ② 真实审计 query | 现役 + 归档审计去重后等距抽 150 条 recall query | **无人工标注** | 只看行为差异（top1 覆盖率、证据不足率、与基线 top5 重合度），不作为质量真值 |

### 1.2 四个变体（同一批候选、同一批 query、同一套生产函数）

- `baseline`：现役 64 维行向量 cosine，与加权 query 覆盖率按 λ=0.6 几何融合（`fuseRelevance`），再过 `scoreMemory` 四分量。
- `e5only`：直接把 e5 384 维 cosine 当 relevance（注意：仍过 `scoreMemory`，pinned +0.15 等乘数不变）。
- `e5fusion`：把融合的 cosine 输入从 64 维换成 e5 384 维，覆盖率与 λ 不变。
- `hybrid`：cosine 输入 = 0.5×64 维 + 0.5×e5 384 维，再融合覆盖率（**双后端并存**的迁移形态）。

打分、过滤、融合、分词全部直接 import `forgetting.ts` / `vector.ts`，评估脚本不复制公式；正文 tokenSet 预计算一次（与 P1-8′ 同口径），避免评估自身被分词耗时污染。

## 2. 结果

### 2.1 ① LOO 客观排名（n=300，候选 5663）

| 变体 | Recall@1 | Recall@5 | NDCG@5 | 排名中位数 |
|---|---:|---:|---:|---:|
| baseline（现役） | 27.7% | 55.3% | 0.4292 | 4 |
| e5only（纯 384 维替换） | **0%** | **0%** | **0** | 2787 |
| e5fusion（换 cos 输入） | 28.3% | 53.0% | 0.4162 | 5 |
| **hybrid（双后端融合）** | **30.0%** | **56.3%** | **0.4424** | 4 |

解读：
- **纯 e5 不可用**：调试样例里目标自身相似度 0.96、榜首 0.85，目标却排到第 192 名——原因不是向量错，而是 **e5 cosine 动态范围太窄**，被 `scoreMemory` 里 pinned +0.15 / boost 等乘数整体压过去。稠密余弦不能原地替掉现在的 relevance 口径。
- **只换 cos 输入（e5fusion）不赚反亏**：R@1 +0.6pp 但 R@5 −2.3pp、NDCG −0.013、中位排名 4→5；e5 的语义相似度与现役词覆盖在长中文账本上并没有形成互补优势。
- **hybrid 是唯一全指标不回退的变体**：R@1 +2.3pp、R@5 +1.0pp、NDCG +0.0132（相对 +3.1%）。**增益真实但很小**，远没到值得为它翻包体积、引入 native 模块的程度。

### 2.2 ② 真实审计 query 行为（n=150，无人工标注）

| 变体 | top1 token 覆盖率 | evidence_thin 比例 | top5 与基线 Jaccard | 基线 top1 保留率 |
|---|---:|---:|---:|---:|
| baseline | 0.3784 | 4.7% | 1.000 | 100% |
| e5only | 0.0822 | 0% | 0.041 | 4% |
| e5fusion | 0.3864 | 0.7% | 0.804 | 80.7% |
| **hybrid** | **0.3871** | **0.7%** | **0.875** | **89.3%** |

解读：
- hybrid 的 top1 覆盖率 +0.0087，与 LOO 的小幅改善同向；top5 重合 87.5%，说明它**没有把召回结果大换血**，行为风险可控。
- 本样本的 evidence_thin 基线是 4.7%，**不能与现网 743 次统计的 50.5% 直接比较**：这里是 150 条去重 query 的纯 top5 相关度口径，没有经过现网的硬熔断/影子补带/逃生阀回填时点，样本与计算时点都不同。要比较必须重跑同一批 743 条。

## 3. 工程账（本机实测，不拿官方 benchmark 冒充）

| 项 | 数字 |
|---|---|
| 模型文件 | O4 fp32 **235MB** + tokenizer 17MB + sentencepiece 5MB ≈ **257MB**；`model_qint8_avx512_vnni` 只有 118MB，但本机 i5-13600KF 无 AVX512-VNNI，不能用 |
| 安装包体积 | 现役 124MB → 约 **380MB**（若换支持 AVX512 的 CPU 且用 int8，约 260MB） |
| 冷加载 | **1.7s**（首次 recall 额外延迟） |
| 全库重嵌入 | 5663 条 **544.9s / 9.1 分钟**（安装期做不可接受，必须随包下发预计算向量或后台任务） |
| 每次 recall 增量 | query embed **9.1ms** + 384 维全库 cosine **5.8ms** ≈ **15ms**（相比 P1-8′ 已省的 241ms 不算大） |
| 运行时依赖 | `onnxruntime-node` 是 native `.node`，需 `asarUnpack`/`extraResources` + electron-rebuild；`embedSync` 还被 9 个模块直接 import，不能只改 recall 一处 |
| 确定性 | int8 跨 CPU 指令集有数值漂移（外部资料），随着维度从 64→384，阈值与历史向量迁移都要重验 |

## 4. 门槛判定与建议

**判定：不达标，P1-6 生产化暂缓。** 理由按权重排：

1. **收益不够大**：最好变体只 +2.3pp R@1 / +0.013 NDCG@5；以 124MB→380MB 的包体积和 native 工程复杂度换这个增益，不成比例。
2. **纯替换方案被实测否决**：e5only 在客观 LOO 上 R@1=0%，说明「换模型就变聪明」的假设不成立；要做只能双后端 hybrid，复杂度再上一层。
3. **迁移成本硬**：9.1 分钟全库重嵌入 + 历史向量维度不兼容（64 vs 384，cosine 维度不一致按 0 分），必须设计随包预计算向量或后台迁移，属于另一个量级的工程。
4. **已有更划算的优化**：P1-8′ 零依赖省 241ms，投入产出比远高于 P1-6。

**保留结论**：本评估脚本与结果留在仓库，作为以后重评的基线（只读工具，不进生产链路）。若将来要重启 P1-6，先达到两个前置门槛再谈生产化：① 在**有人工标注**的 query 集上 hybrid 相对基线 NDCG@5 提升 ≥5pp；② 模型随包离线 + SHA256 校验 + 安装期不做 9 分钟重嵌入的方案落地。P1-7 reranker 前置依赖 P1-6 且延迟冲突，继续暂缓。

## 5. 边界与诚实声明

- 本次模型是 **O4 fp32 235MB**，不是最初方案里估的 118MB int8——本机 CPU 不支持 AVX512-VNNI，实际能用的文件就是 235MB；包体积估算据此修正。
- LOO 的 query 由正文首行派生，天然偏袒词面匹配（baseline 的强项），可能对 e5 不利；这是为了与既有评测可比而保留的口径，不能当成 e5 能力的上界。因此在真实审计 query 上另跑了行为对比，两者结论方向一致（小增益，非质变）。
- 150 条审计 query 无人工标注，top1 覆盖率只是代理指标；**本评估没有证明 e5 在真实用户问题上「更懂语义」**，只证明了在这个打分管线和这批数据上没有质变收益。
- 全程未写账本、未改 `growthConfig.ts` / `agent.ts` / `vector.ts`；临时安装的推理库用 `--no-save --no-package-lock`，`package.json` 与锁文件未改；模型与临时依赖都在系统临时目录，不随包分发。

### 本次问题复盘
**① 现象与真正根因**：先前报告把「64 维词袋 → 384 维语义」写成几乎必然的质量跃迁，真跑模型后发现增益只有 +2.3pp R@1——表层是模型维度差，根因是现役 relevance 是「cosine × 词覆盖 × 四分量乘数」的复合信号，单换 cosine 输入撼动不了排序骨架。
**② 我在排查中走过的弯路与浪费的动作**：先用 `--loo 30 --audit 10` 试跑看到 e5only R@1=0%，差点判成向量错位；加 `DEBUG_ALIGN`/`DEBUG_RANK` 才看到目标自相似度 0.96 却被 pinned 文档压到第 192 名——该早点把「相关度绝对值」和「分数构成」一起打印。另外初始脚本没预计算正文 tokenSet，评估自身也会被分词拖慢，改完才敢全量跑。
**③ 修复点与防复发机制**：把四个变体绑在同一批候选/query/生产函数上，LOO 真值口径 + 审计行为口径互相校验；结果落 JSON + 日志可复跑；报告明确写「e5only 不可用 / hybrid 只小赚」的判据（R@1、NDCG、中位排名三项同向），防止下次只挑一个好看的数字上生产。
**④ 遗留未解项与下一步**：没有人工标注 query 集，语义收益上界仍未测；int8 在其他 CPU 上的数值漂移未验；若重启 P1-6，先按第 4 节两个前置门槛立项；P1-8′ 尚未打包/提交（等工作区确认），折叠卡测试扩展（8→12 例）也仍待提交。
