## 1. 观察指标（全部来自 `audit.jsonl`，不手工填报）

| 指标 | 含义 | 为什么用它 |
|---|---|---|
| **top1 覆盖率均值** | 命中排第一的那条，正文覆盖了提问 token 的比例 | 最贴近「搜得准不准」：命中再多，覆盖不了提问也没用 |
| **未命中率**（hits=0） | 一次都没搜到的比例 | 最直接的「搜不到」 |
| **证据不足率**（evidence_thin） | 所有命中分都 <0.3 的比例 | 「有结果但都很弱」，比 0 命中更隐蔽 |
| 平均命中数 | 每次召回返回几条 | 掉得太低说明候选被压死 |
| 重复 query 占比 | 同一 query 被重复发起 | 弱信号：可能上次没搜到/不满意 |
| 首调召回合规率 | 可靠会话中第一次调用就是 `recall_memory` | 验批次47 的 L1/L2 是否真的在起作用 |
| 延迟 p50/p95/max | 每次召回耗时 | 验 A 方案的全量分词代价（预期 +45ms 量级） |

## 3. 判定标准（事先写死）

一周结束后按下表判定，**任一条触发就升级**：

| 指标 | 达标（停在 A） | 观察（继续收集） | 升级（走 B） |
|---|---|---|---|
| top1 覆盖率均值 | ≥ 0.25 | 0.15 – 0.25 | < 0.15 |
| 未命中率 | ≤ 10% | 10% – 20% | > 20% |
| 证据不足率 | ≤ 15% | 15% – 35% | > 35% |
| 延迟 p95 | ≤ 1500 ms | 1500 – 2500 ms | > 2500 ms（先加 token 缓存，仍超则走 B） |
| 重复 query 占比 | ≤ 10% | 10% – 25% | > 25%（同时人工抽检 10 条 query 看是否语义失败） |

**走 C 的独立触发条件**（与上表并列）：人工抽检里出现 ≥3 例「语义明显相关但一个词都不重合」的检索失败
（例：问「服务有点慢」，记忆里写「P99 延迟」——A 方案对这类问题**天然无能为力**，只能靠 C 或接向量模型）。

**升级结论必须附证据**：指标表 + 至少 5 条真实 query 的命中情况（query / top1 是啥 / 覆盖了什么）。

## 4. 采集方式

- **脚本**：`tools/recall-stats.mjs`（只读审计与账本；`--snapshot` 只往 `specs/reports/recall-snapshots.jsonl` 追加一行）。
- **节奏**：每天 21:00 自动快照一次（自动化任务「召回A方案·周数据采集」，有效至 2026-11-19）。
- **一周后**：2026-11-19 出一份 `specs/reports/RECALL-WEEK-1.md`，含指标对比表、抽检样本、判定结论。
- **人工抽检**：一周内我至少抽 10 条真实 query，逐条看 top1 是否真的回答了提问（这是自动化算不出来的部分）。

## 5. 已知干扰与风险

1. **样本量**：若一周内 recall 少于 30 次，所有「率」都不足以下结论，只能给方向，结论要写「样本不足」。
2. **客户端混杂**：审计里的 `client` 有 20+ 种（含验证脚本的自造名），统计时以 `client=workbuddy`、
   `qoder-*`、`claude-code` 等真实使用为主；自造名（`verify-*`、`probe`、`walk`）应剔除后再看。
3. **老审计缺字段**：`latency_ms` / `evidence_thin` 只有较新版本才写，覆盖率会标在输出里，不高估。
4. **A 方案的固有边界**（不是 bug）：不做同义/近义扩展；无共有词直接 0 分。
   所以「语义相关但用词不同」的失败**不该记在 A 头上**，它是走向 C 的证据。
5. **别为了指标好看调 λ**：λ 是从 leave-one-out 评测里选的 0.6，那个评测结构性偏袒大 λ。
   真要用数据调，必须用这一周的真实 query，而不是再跑一遍评测器。
