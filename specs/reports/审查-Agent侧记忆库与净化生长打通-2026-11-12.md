# 审查报告 — Agent 侧记忆库使用与净化生长数据是否打通

> **方法**：源码实读（规格声称与代码实际分开列，冲突以代码为准）。全程只读，未改运行时、未跑写操作。
> 行号对应 2026-11-12 工作区 `main`。相对路径均以仓库根为基准。

## 0. 一句话结论

**物理账本确实共享，且存在唯一一段真实闭环**（recall 命中 → `access_count` / `last_access_time`
→ freshness / boost → 后续召回排序与衰减存活）；
但「**Agent 的使用与反馈驱动记忆自我进化**」这条目标链基本断开：

- `feedback` 只改 `confidence` 一个标量，不降档、不重炼、不 ban、不断引用边；
- 「自生长」回归调的是**写入查重权重**，完全不碰召回排序权重（召回权重是写死常量）；
- `gc_report` 与净化生长页读同一账本，却是互不相交的两套计算；默认 `dry_run=true` 零写入，
  报告里没有任何 Agent 侧信号，页面也从不读 `action='gc'`。

## 3. 最关键的 3 个缺口（按对目标的影响排序）

1. **召回排序参数完全不可进化（最致命）**。规格声称「每周回归 mode_weights」「命中率低 → 降阈值 / 加速遗忘」
   （`specs/需求规格书_UI页面设计.md` :685、`specs/需求规格书.md` :885–898），
   但真实回归只调写入查重权重；`SCORE_WEIGHTS = { w_f:0.35, w_i:0.30, w_c:0.15, w_a:0.20 } as const`
   （`forgetting.ts` :18）与 `hardFilter` 永远不变。结果：无论命中率多低、Agent 反馈多少次，
   Agent 看到的召回排序与过滤参数恒定。
   `src/web/growth/logic.ts` :74–106 的 `evaluateOptimizations` 注释即「只读指标驱动，不改指标」，只产状态徽标。

2. **Agent 反馈信号没有回到净化生长的因果链**。`coreFeedback` 只 ±`confidence`（confirm +0.1 / reject −0.05，
   从默认 0.5 需连续 9 次 reject 才触到 `hardFilter` 的 0.05 阈值）、加 `reinforce_count` 或挂 `conflict_id`；
   `runForgettingCycle` 从不读 `recall` / `memory_op` / `mcp_call` 审计，不知道哪些记忆被反复命中或反复拒绝。
   「用得多的留、被否掉的退」只剩 `access_count`/`last_access_time` 一条隐式信号，
   且 `boost = min(1, access_count/10)` 在 10 次命中后饱和（`forgetting.ts` :60）。

3. **Agent 侧与桌面侧的「净化」是两套不相交的账**。`gc_report` 默认 dry_run → 零写入零审计；
   其 10 项分层报告在 growth/lifecycle 页完全不展示（页面只认 `schedule_run`/`growth_op`/`weight_tuned`/
   `recall`/`memory_op`），报告里也不含 client 维度、省量、反馈分布；反过来页面没有 recall 次数、
   `saved_tokens`、按 Agent 拆分、首调合规率。Agent 调 `gc_report` 看到的数字，与用户在「净化生长」页
   看到的数字**毫无对应关系**。
