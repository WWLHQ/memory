- **L0 是密文落盘层**：不参与检索/查重；写入需管理员在安全页解锁写密钥（只加密，不能解密）；查阅需管理密码，或被授权账号凭 `grant_id + 一次性密码`，会话 5 分钟中断即锁定并作废授权（§4.4）。旧明文 `content_orig` 存量由批次37-C 的「L0 存量拆分迁移卡」封存后搬进 L0 库（搬前自动双库备份）；v1 遗留信封升级仍走安全页**独立的「L0 旧数据迁移」卡**（批次38 从 L0 管理卡拆出；`l0:migrate`，需旧密码，且**写密钥没解锁就不给点**）。
- **L0 与 L1–L6 拆成两个库文件（批次37，回答「L0 和 L1-L6 要分 2 个文档存储」「首次启动强制指定两个库位置」「两库都要备份」「万一忘记密码数据就废了」「删的只是 L1–L6 那份库，直接从 L0 重新生成」）**：
  - **37-A 拆库**：`FileL0BlobStore`（`src/core/memagent/l0Store.ts`）把 L0 原文独立成 `memories.l0.json`（0600，`{version,items:{[mem_id]:{envelope,sealed_at}}}`），**只收 `isSealedL0` 认可的 v2/v1 信封，拿到明文直接抛 `L0NotSealedError`**——明文永远进不了 L0 库，这是「拆库」而不是「换个地方躺明文」。记忆库行上只留 `has_l0`，查阅时经 `l0:blobs`（需会话）批量回读密文、再经 L0 会话解密。
  - **37-B 首启强制向导**：`setup.html` + `src/web/setup/SetupPage.tsx`（第 20 个入口）。门禁判据在**主进程**（`isWizardIncomplete()` = 指针里的 `ledgerDir` + `l0Dir` + L0 管理密码 + 恢复卡已导出四件事），页面只是载体——绕过页面也进不了数据面，各条 IPC 各有自己的会话/管理员闸门。`setup:finish` 只在**本次真导出过一张恢复卡**才落 `setupDone`（用户拍板：强制先导出才能继续）。升级上来的老指针没有 `setupDone`，**照样进向导**（用户拍板：升级也走强制向导）。向导内改选两库位置后要重启才生效（路径在 `app ready` 前解析）。
  - **37-D 双库备份**：`src/electron/backupFiles.ts` 是纯函数配方（`memories-` / `meml0-` / `l0key-` 三前缀 + 同一时间戳，各自按 `keep` 滚动，互不挤占），定时/立即/内核变更前（`backupBeforeKernelChange`）都走它——**只备记忆库会让 L0 原库成为唯一没有退路的那一份**；缺哪个源就在回执里明说缺哪个。
  - **37-G 恢复码与恢复卡**：忘记 L0 管理密码时唯一的找回通道。原理是**同一个 DEK 包两份**（`admin_wrap` 用管理密码派生 KEK、`recovery_wrap` 用恢复码派生 KEK），恢复码是 32 字节 = 256bit 随机数、**不是密码的衍生物**（弱密码连累不到恢复码，恢复码也推不出密码）；卡面纯文本（可打印/可抄/存密码管理器，不依赖本应用才能读），带库指纹与「对应文件」路径；**一次性口径**：用过即作废并当场换新码，新卡必须重新导出；状态接口只回「有没有/指纹/时间」，码明文只在发码那一次的返回值里出现一次，绝不进日志与审计；导出走主进程原生「另存为」，卡面不落数据根。**红线（卡面、恢复卡正文、§9 三处都写了）：管理密码与恢复码同时丢失 = L0 原数据库不可恢复**，解密能力没有任何服务端兜底。
  - **37-E 按 L0 重建 L1–L6**（`rebuild.ts` + `l0:rebuild*` + 安全页 `RebuildFromL0Card`）：不重新采集、不动游标，用库里已有原文重走写入管道（原文→质量门→新 L1→可选逐层 L2–L6→重算 sha256/向量/规格戳）。边界：① 原文只两条来源——行上历史明文，或经**管理员的 L0 查阅会话**解密，本通道不开新的解密口子，`view_locked` 行在**备份之前**就整轮拒绝；② 取不到原文（`no_source`/`broken_link`/`view_locked`/`bad_envelope`）与 `pinned`/`locked` 行**一行不碰**，只计数——重建不是顺手清理，没有证据就删等于凭空丢数据；③ 「同时用 LLM 重炼 L2–L6」是显式开关且要求 `llmGateway.usable()`，不勾就把 L2–L6 清空并如实记 `refined_by=stub`（预览用 `rebuild_deep_cleared` 提前告知会清多少行）；④ L0 原文与新正文一律不进日志/审计/回执，每行只记来源字段、产出层名、计数；⑤ **适用边界（批次41-O 补）**：重建救的是**整份 L1–L6 库丢了 / 要整库重造**（原文还留在 L0 库里或行上），它**救不回逐行删除**——某行被 `ledgerReset`（清空重采）/ `rejudge`（规则重判）/ 手动删除删掉后，其 L0 密文被**同步销毁**，重建找不到原文就按「取不到原文」一行不碰。逐行删除的唯一退路是执行前落的那份备份目录，所以批次41-O 在两张卡的预览/回执里都明写「连带销毁 N 条 L0 原文」（`with_l0_cipher`）。
  - **诚实边界**：纯浏览器（`npm run dev`）无主进程 → 向导与五张 L0 卡（管理 / 拆分 / 旧数据迁移 / 恢复 / 重建）都如实显示不可用，绝不用页面内存对象冒充真文件；`setup.html` 有点击级 E2E（`e2e/setup.spec.ts` 12 例，跑真 dist 产物：不打桩验诚实降级，打桩 `window.api.setup.*` 验页面闸门/发码/导出/真导航，桩镜像 `main.ts` §6e 的返回与拒绝文案），但**该栈没有 Electron 主进程**——`setupDone` 落盘、主窗口真被拦在向导、原生选目录/另存为、真密钥环与 DEK 封装、SPLIT/REBUILD 路径**仍只有单测与实机走查覆盖**（见批次37 手测报告 §8）；拆完库后 `memories.l0.json` 是**唯一的原件副本**，请与密钥环、恢复卡**分开备份存放**。

  - **就地解锁卡 `L0WriteUnlock.tsx`（新增，`src/web/shared/`）**：管理员当场输 L0 管理密码走 `getKernel().l0UnlockWrite`（主进程 `requireAdmin`）→ 成功 `onUnlocked?.()`；**普通成员 / 未登录不给点了必然失败的按钮**，只如实说明「需管理员在安全页 → L0 管理 → 写密钥解锁」。密码边界：只进这一次调用，成功与失败都立刻清空，不进日志与审计（IPC 层只记 `{ms}`）。
