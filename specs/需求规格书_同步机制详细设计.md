# 同步机制详细设计（全端同账号云同步）

> 配套：《需求规格书》19.10/19.11、《需求规格书_内核API契约》、5.1（双通道采集）、5.4（幂等）、9.7（冲突裁决）、4.3（审计）、18.2-A（租户 ID）。
> 本设计把 19.11 的"全端同账号同步"落到**可实施**：同步身份、主源与镜像、离线回传、冲突裁决、对账周期、审计归因——并**再次讨论**几个容易含糊的点。
> 目标：**6 端（桌面/Web/移动/macOS/Linux/CLI）同一账号数据一致，离线不丢、回传幂等、冲突可裁决、全程可审计。**

## 1. 同步身份与数据归属（再次确认）

**同步身份 = 账号（18.2-A）**：`enterprise_id` + `team_id` + `user_id` 三元组，由端壳登录时注入内核，**全局注入、禁手填**（0.1 红线 R1）。

| 数据类 | 归属粒度 | 同步范围 |
|---|---|---|
| 项目记忆（fact/decision/pitfall/insight/context） | **team_id 级**（同团队共享） | 同 team 全端同步 |
| 个人偏好（preference） | **user_id 级**（微信式 9.2，跨 Agent/项目） | 同 user 全端同步 |
| 租户/团队 | enterprise_id/team_id | 仅租户内 |

> **再次确认点①**：你说"以上各端只要是同一账号均需要同步"——落地为**同 `user_id`+`team_id` 即同步**。不同账号即使在同机（CLI 系统库 vs 个人桌面库）也**不混入**（19.10 红线⑥ / ②），这是"账号"边界，非"机器"边界。

## 2. 主源与镜像拓扑（桌面 = P0 主源）

```
                       ┌─────────────────────────────┐
                       │  服务端中枢（Postgres+pgvector）│
                       │  = 同账号全端镜像 + 9.7 裁决中枢 │
                       └───┬─────────────────────────┘
        5min 短周期对账 + 每日全量 + SHA-256 幂等
   ┌────────┬────────┬───────┴───────┬────────┬────────┐
   桌面     Web      移动     macOS    Linux     CLI
 (主源↑)  (镜像)  (镜像,离线先写本地) (镜像)  (系统库,team隔离) (命令触发)
```

| 端 | 角色 | 上行（写→中枢） | 下行（中枢→读） |
|---|---|---|---|
| **桌面** | **P0 主源** | 本地库变更实时上行（主源优先级最高） | 读本地库为主，中枢补缺 |
| Web | 镜像 | 写→中枢 | 读中枢镜像 |
| 移动 | 镜像（可离线） | 离线本地先写，联网批量回传（幂等） | 读本地缓存+中枢 |
| macOS | 镜像（走桌面库） | 经桌面库上行 | 读桌面库 |
| Linux/CLI | 系统独立库 | 命令 `sync` 触发上行（team_id 隔离） | 读系统库 |

> **再次确认点②**：桌面端是**主源**（数据最全，有本地库+本地向量索引+全量发现），Web/移动/macOS 是**镜像**。若你的部署是"服务端为权威源、桌面是瘦客户端"，则主源翻转（见 §7 决策项）。默认按"桌面=主源"设计。

## 3. 同步协议（版本向量 + 幂等 + 对账）

### 3.1 变更捕获
- 每条 `memories` 带 `version`（单调 int）+ **vector clock**（`{端: 版本号}`）+ `sha256`（内容指纹，5.4 幂等）。
- 写操作（recall 不写，write/gc/裁决写）本地先落盘 + 记 `version++` + 更新 vector clock。

### 3.2 上行（回传）
| 触发 | 行为 |
|---|---|
| 桌面 | 实时上行（主源，低延迟） |
| Web/macOS | 变更后即上行（在线） |
| **移动（离线）** | 本地先写，恢复网络后**批量回传**；按 `sha256` 去重（**幂等，不产生重复**） |
| CLI | `memagent sync` 命令触发（批量） |

### 3.3 下行（拉取）
- 镜像端定时拉取中枢增量（`since=version_cursor`）。
- 桌面主源下行仅补"自己没的、别人改的"。

### 3.4 对账（5.1 双通道思想复用）
| 周期 | 动作 |
|---|---|
| **5min 短周期** | 各端 session_id/version 比对中枢，补缺、补漏（"主通道"） |
| **每日凌晨全量** | 全量对账 + 一致性校验（sha256 全表比对，"补偿通道"） |
| 冲突 | 见 §4 |

> 这就是 5.1"Webhook 主 + API 拉取补偿"在**端同步**上的同构应用：短周期=主通道，每日全量=补偿通道，SHA-256 幂等保证不重不漏。

## 4. 冲突裁决（9.7 状态机 + 人工队列）

**冲突定义**：同一 `team_id` 下同一 `mem_id`（或同 project_id+user_id+category 语义冲突）在**多端并发修改**。

| 冲突类型 | 自动策略 | 兜底 |
|---|---|---|
| 同 mem_id 同字段不同值 | vector clock 判因果；**有偏序取晚者**（last-writer-wins，带时间戳） | 有偏序且都晚 → 进 9.7 裁决队列（P8） |
| 语义冲突（两条记忆互斥） | 6.1 查重 5 维 + 9.7 状态机自动裁决（如"废弃旧洞察"） | 高置信冲突 → 人工裁决队列 |
| 偏好冲突（user 级） | user_id 级 last-writer-wins | 进裁决队列 |

**裁决队列（P8 裁决页）**：
- 自动裁决失败的冲突 → 挂起，记 `conflict_id` + 双方版本 + 两端 `form`。
- 管理员/用户裁决后回写"获胜版本"，败者转 `archived`（9.7 生命周期）。
- 全程审计（`action=conflict_resolve`）。

> **再次确认点③**：默认**自动 last-writer-wins（带 vector clock 因果）**，只有"语义互斥/高置信"才进人工裁决队列——避免每次小改都打扰用户。若你要"所有冲突都人工"，需改 9.7 阈值（更保守）。

## 5. 离线与重连（移动端重点）

| 场景 | 行为 |
|---|---|
| 移动断网写记忆 | 本地 SQLite 先写（`pending_sync=1`），不打断用户 |
| 恢复网络 | 批量回传，`sha256` 幂等去重，清 `pending_sync` |
| 期间中枢有更新 | 回传完再拉取增量，合并 |
| 离线期间同账号桌面端也改了 | 上行时 vector clock 检测冲突 → 走 §4 |
| 长期离线（>对账周期） | 每日全量对账时一次性对齐 |

## 6. 审计归因（全动作可查，4.3 / 18.2-E）

每次同步相关动作写审计，字段固定：
```
sync_audit {
  request_id,            // 审计链主键
  action: "sync_up" | "sync_down" | "sync_reconcile" | "conflict_resolve" | "sync_fail",
  form: <端>,            // 在哪个端发生（19.10，可归因"这条是桌面回传的"）
  user_id/team_id,
  mem_id(s), version, sha256,
  ts, detail
}
```
- 日志记录页可查同步事件（level=error 的 `sync_fail` 置顶）。
- 可回答"这条记忆是哪端、何时、以何版本写入/回传/裁决的"。

## 7. 同步决策（已拍板并写死：桌面主源 + 自动 LWW + 有 Postgres 中枢）

> **三项决策已锁定**（用户确认），§2 拓扑、§3 协议、§5 离线逻辑即按此组合实现，不再保留"可选翻转"。若未来需变更，须重走本章节决策流程并同步改 §2/§3/§5。

| # | 决策 | **锁定值** | 落点 |
|---|---|---|---|
| ① | **主源** | **桌面本地库 = P0 主源**；Web/移动/macOS = 服务端镜像；CLI/系统库 = 按 team_id 独立 | §2 拓扑（桌面为"主源↑"，其余为"镜像"） |
| ② | **冲突自动度** | **自动 last-writer-wins（vector clock 因果判定）**；仅"语义互斥 / 高置信"进 9.7 人工裁决队列（P8） | §3.4 冲突、§4 裁决 |
| ③ | **服务端中枢** | **要**：Postgres + pgvector，承担全端镜像 + 9.7 裁决中枢 + 5.1 对账 + 离线回传幂等账本 | §2 中枢、§3.2 上行、§5 离线 |

### 7.1 锁定理由（详细讨论存档）

**① 桌面主源**：桌面端能力最强（全量发现 + 本地库 + 本地向量索引 + 跨 Agent 借算力，19.10），数据最全，定为权威源最自然。代价是"桌面不在线时 Web/移动读旧镜像"——由 ③ 的中枢保留最新镜像缓解（桌面离线时中枢镜像"暂代"）。

**② 自动 LWW + 仅语义冲突人工**：多端同步若"每次小改都人工裁决"会打扰用户；LWW（带 vector clock 因果）对"同字段不同值"自动收敛，只有"语义互斥"（两条记忆内容矛盾）才进 9.7 队列。被覆盖版本转 archived（9.7 生命周期）不物理删，可恢复，误覆盖代价可控。

**③ 有 Postgres 中枢**：中枢承担"全端镜像 + 裁决 + 对账 + 离线幂等账本"，是"全端同账号云同步"的枢纽；移动端离线回传需 sha256 去重，必须有中心账本。P2P 被否（移动端离线能力弱 + CLI 两两握手 N² 复杂度）。

**综合**：§2 拓扑图即"桌面主源 + Postgres 中枢 + 其余镜像"的三件套；§3 协议（版本向量 + LWW + 对账）与 §5 离线（本地先写 + 批量幂等回传）均按此锁定。

## 8. 验收用例（同步级）

| 用例 | 操作 | 期望 |
|---|---|---|
| 桌面→Web | 桌面写一条项目记忆，Web 同账号登录 | 5min 内 Web 命中（镜像），审计 `form:web`/`sync_down` |
| 移动离线 | 移动断网写 3 条 | 本地先存，联网批量回传，sha256 幂等无重复，`pending_sync` 清零 |
| 离线冲突 | 移动离线写 A，桌面同时写 A | 回传时 vector clock 检测冲突 → LWW 取晚，或进 9.7 队列 |
| CLI 隔离 | Linux `memagent sync`（不同 team） | 系统库按 team_id 隔离，不混入个人桌面库 |
| 对账兜底 | 5min 短周期漏一条 | 每日全量对账补回，sha256 校验一致 |
| 审计可查 | 日志页查 `sync_*` | 可见各端同步事件 + 冲突裁决，按 form/时间过滤 |
