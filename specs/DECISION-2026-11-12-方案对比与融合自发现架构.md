# 方案对比与融合决策：分层收敛，而非互斥取舍

> **一句话结论**：前几轮把「判据 / 决策 / 载体 / 止血」四个不同层的方案当成互斥选项反复替换，越讨论越重，而 11-06~11-10 的根因一直没修。更合适的做法是**按层收敛而不是按方案取舍**：判据层做进现有内核（零架构改动、当天可验、不依赖任何进程形态），止血并行最优先，服务化从「防复发的前置条件」降级为「独立演进的终局」，并**复用仓库 2026-11-05 已有的 backend 守护设计**，不另起炉灶重写 4053 行 `main.ts`。
>
> **本文状态**：2026-11-12 落盘；**§6 的 P0 已落地**（实现回执见 §6.1，2026-11-12），T1~T8 仍为设计决策、尚无实现代码。本文其余「待实现/待拍板」口径均指 T1~T8，不再包含 P0。

**三个改变结论的发现**：

1. **判据层完全不依赖进程架构**。核查结论：`collect_round_receipt` 新 action 只需加一个常量（`auditLog.ts:89-96` 的 `parseLine` 只校验 `typeof action === 'string'`，无白名单）；守恒埋点集中在 `sessionCollector.ts:357-603` 同文件；只读看护可直接复用 `FileAuditLog(file, {readonly:true})`（`auditLog.ts:135/277-294`）；IPC 回显字段可原样不动。**「桌面端在线时自证」无需先动任何架构**。
2. **守恒等式的左值现在根本拿不到**。`ScanResult`（`sessionCollector.ts:323-332`）只有 `{collected, deduped, roleSkipped, skipped[], items[], cursors, ts}`，**没有** `matchedFiles / candidates / parsed / rejected`；`declared` 无从计算。对账要落地必须先补埋点 —— 这是所有方案里最该先做、且风险最低的一步，此前四轮讨论都默认它已存在。

## 1. 方法：先把方案归到四层

前几轮定不下来的原因不是方案不好，而是**拿不同层的东西互相否定**：用「握手」（判据层）去否定「守恒」（判据层）尚可，用「服务化」（载体层）去回答「怎么提前发现异常」（判据层）则答非所问；用「二选一」（决策层）去替代「sidecar」（载体层）同样错位。

```
L0  止血层  ← 修当前数据（唯一真正修 11-06 事故的动作）
L1  判据层  ← 怎么知道坏了（缺回执 / 账不平，零阈值）
L2  决策层  ← 坏了怎么办（三态 + 二选一 + spool）
L3  载体层  ← 谁来跑判据（现状单进程 / sidecar / backend 守护）
```

**核心取舍**：L1 与 L3 解耦。L1 是纯函数 + 埋点，L3 怎么换都不影响它；反过来 L3 再强，也回答不了「路径漂移导致 0 入库」。所以 **L3 不该是 L1 的前置条件**。

## 4. 融合方案：「四层收敛」

### 4.1 设计原则

1. **判据与载体解耦**：L1 是纯函数 + 埋点，写进现有内核，桌面端在线即生效；L3 无论选现状 / sidecar / backend，L1 一行不改。
2. **两条确定规则、零阈值**：`缺回执 > 一个调度周期` → 一级；`balanced=false` 或 `declared>0 && committed=0` → 二级。**不允许静默返回 0 条**。
3. **左值必须独立取证**：`declared` 不能来自采集器自己的扫描结果（否则路径漂移时 `declared=0`、账也平）。来源三选一或组合：① 注册表声明的 `probeGlob` 独立 `stat` 计数；② 契约自注册 / discovery 发现的活跃源；③ canary 注入的已知输入（**保证静默期 `declared ≥ 1`**，这是防漏报的关键）。A1/A2 在这里被保留为**取证手段**，而不是判据。
4. **回执无条件产出**：挂 `onScan` 末尾 / `finally`，**不能**挂 `main.ts:3172-3174` 游标推进点（只有成功轮才执行，失败轮不写盘）。
5. **决策权交人 + 复验销警**：沿用 B2；干预后自动重跑 canary + 对账复验，不通过不销警。
6. **诚实边界**：宿主 SDK 的 `internal_error` 改不动，只如实提示；`list_projects` 静默返空改带 `degraded:true`，`E_BUDGET_FUSE` 真 throw。

### 4.2 L0 止血（并行最优先）

E1 提到 **P0**：WorkBuddy `.workbuddy/projects/*.jsonl` 源 + `workbuddy-jsonl` parser（样本格式已确认 `{type:'message', role, content:[{type:'input_text'|'output_text', text}]}`），回填 11-06~11-10。验收硬指标：**回填产出 > 0 条新记忆**。Trae/Qoder SQLite reader 排 P2（需先探明 chat 正文表）。

> 理由：所有 A/B/C 方案都只是「下次早点知道」，不修当前数据。把它们排在止血前面是本轮之前最大的顺序错误。

### 4.5 L3 载体层：可插拔 + 复用既有蓝本

| 阶段 | 形态 | 触发条件 | 说明 |
|---|---|---|---|
| 默认 | 现状单进程 | 桌面端在线 | L1 全部生效；无需任何新进程 |
| 可选插件 | 极窄 sidecar（8205，默认关） | 需要「关机期间也读得到状态」 | 职责**收缩为只读**：探 8204、读 `audit.jsonl` 回执链、答状态、托管 spool、发通知。**canary 由内核进程执行**，sidecar 只检查 canary 回执是否按时出现 —— 消掉 C1「不碰库却要跑 canary」的自相矛盾 |
| 终局（用户已要） | 登录自启常驻服务 + 桌面端纯 UI | 独立于防复发，单独拍板 | **按 `MCP运维与多Agent写入规范.md` §1.4 阶段 0→1→2→3 推进**，不另编四步 |

终局的四条安全补偿（用户已明确要开机自启，此处不是打折，是把语义补齐）：

1. **L0 DEK 常驻内存**：服务进程收不到 `powerMonitor` 锁屏/休眠钩子（`main.ts:4030-31`），必须补空闲自动锁定（建议 30min）+ 桌面端在线时转发锁屏事件；`l0:decrypt` / `l0:recoveryExport` 绝不回吐 DEK / 恢复码。
2. **单写者**：遵循运维规范 §1.7「阶段 2 前绝不能 main 与 backend 同时写」；采集与 reconciler 只归服务，`collector-cursor.json`（`main.ts:3178-3186` 裸 `writeFile` 无锁）必须先加 `<db>.lock` 式 O_EXCL 锁，否则双写丢更新。
3. **鉴权边界**：`sidArg()`（`preload.ts:14-20`）由受信 preload 注入，HTTP 化后改 `x-session-id` + Origin/CSRF + 逐端点 `requireSession/requireAdmin`；`mcpHttp.ts:488` 拒 Origin → 渲染层走 BFF，不能直连 8204。
4. **用户控制权**：安装时显式勾选自启（默认关）、托盘「暂停采集 / 停止服务 / 自启开关」、卸载停进程 + 清自启项；状态栏常驻显示 `ok / degraded / service_off`，**绝不把「进程活着」显示成「管道正常」**。

> 真 Windows SCM 服务不选：Session 0 + LocalSystem 读不到 `%APPDATA%/MultiAgent Memory` 数据根、无法弹托盘/对话框、需管理员安装，与 `nsis.perMachine:false` 冲突。用**用户级登录自启常驻进程**（`HKCU\...\Run` / 启动文件夹 / 任务计划）即可拿到同样语义。

## 7. 三道闸门与交付约束

每步按 `specs/开发纪律_三道闸门.md`：

- **A 影响面回归**：影响面清单 + `verify:fast` / `test:gate` + 静态门禁 + `code:index:check` + 既有行为未变。纯文档改动时以 `typecheck` / `oxlint` / `code:index:check` / `check:no-demo` / `python tools/validate_project.py` 为准。
- **B 效果验证**：每条 AC 正向端到端，断言状态/审计**真的变了**；只读类反向断言**真的没变**。
- **C 变异验证**：至少一次代码级变异（如临时把 `evaluateHealth()` 恒返回 `healthy`、或允许 spool 写入 token → 指定用例必须红 → 原样还原 → 必须绿）+ 输入/状态变异矩阵。纯文档改动时用「移走新文档 → `code:index:check` 判红 → 还原判绿」。

每步收尾：收尾五步（跑验→扫→清→核→报）→ `npm run code:index -- --write` → conventional commit（含 Why/What/影响范围 + `Co-Authored-By`）→ push。**每步先展示成果等人工确认，不连跑多步。**
