# 召回模式内核增量规格条款（P2-9 · 草案）

> 背景：`src/core/memagent/recallModes.ts` 已定义 `conflictRule` 五模式条款、`COMMON_INVARIANTS` 与 `MODE_FEATURE_WORDS`，但三项能力尚未接线：① `conflictRule` 全 `src` 零消费方，多模式相斥实际只靠 `MODE_PRECEDENCE` 数值排序；② `critical` 最低深度「L3+L4+L2」仅为占位符字样；③ §7.2「词表/权重可热更」但 `MODE_FEATURE_WORDS` 是 `const`、`ModeDispatchConfig` 生产调用不传。

## 条款 1 · conflictRule 冲突仲裁生效（P2-9-①）

### 1.1 规格依据
- `需求规格书.md:244`（§2.4.2 公共不变量表「冲突原则」）：冲突仲裁按**当前模式**的「核心冲突规则」列执行；「高优先级层级」指**该模式内排位更高**的层级（非全局 L5 最高）；组装 prompt 时对每对可能冲突的命中条目内置仲裁说明：`[冲突] 条目A(层/来源/时间) vs 条目B(层/来源/时间) → 本模式=X → 裁定以 Y 为准，Z 作参考`。
- `需求规格书.md:349`：模式互斥裁决与 17.2 冲突优先级框架共用，不另立山头。
- `recallModes.ts:35/53/63/73/83/93`：五模式 `conflictRule` 人话条款（已定义）。

### 1.2 语义定义（已批准 · 2026-11-25）
1. **仲裁对象**：同一召回结果内，标记 `conflictWith` 的命中对（由去重/合并阶段产出；当前 mock 见原型用例 c8）。只有被显式标记冲突的条目对才仲裁，不自行推断语义冲突。
2. **裁决依据**：取 `resolved.mode` 对应 `RECALL_MODE_SPECS[mode].conflictRule`；「高优先级层」按该模式 `selectPriority` 数组下标判定（下标小者排位高），**不按全局层序**。
3. **裁决结果**：每对冲突产出 `{ winner, loser, rationale, loserRole }`——`winner` 为排位高者；`loserRole` 取「历史参考 / 待核实 / 注脚 / 特例」之一，映射自模式 `conflictRule` 尾句；`rationale` 直接引用该模式 `conflictRule` 原文，不改写。
4. **与 17.2 的关系**：17.2 的 7 条全局优先级（用户显式删除 > 锁定 > 置顶 > 合规审计 > 旧生命周期状态机 > 新自动遗忘 > 默认检索）是**硬约束前置**——先按 17.2 过滤/排序，再对仍冲突的对按本条款仲裁；17.2 已裁决的对不重复仲裁。
5. **prompt 内置说明**：每条 winner 的上下文文本前插入 `1.2` 规格给定的 `[冲突] …` 说明行，计入 `payload_tokens`（与 §2.4.1 预算同口径）；超预算时该说明行随 winner 条目一起按 `trimOrder` 裁剪，不单独保留。

### 1.3 接线点（拟）
- `src/core/memagent/agent.ts`：组装 prompt 段（`selectRecallBackground` 之后、预算裁剪之前）新增 `buildConflictNotes(hits, mode)`，输出说明行数组；与 `recallInsight.ts` 的回显同源（回显也显示 `[冲突]` 说明）。
- 复用 `modeSpec(resolved.mode).conflictRule` + `selectPriority`，不新立第二套裁决表。
- 单测：`conflictRule` 五模式各一例（winner/loser/rationale）；17.2 前置优先一例；超预算裁剪一例；同模式内层级排位一例。

### 1.4 验收判据
- 五模式 `conflictRule` 均有消费方（grep 零消费方归零）。
- 同一冲突对在 `critical`（fact_first）与 `task_start`（top_insight）下 winner 可不同（模式内排位差异），且 rationale 与各模式条款逐字一致。
- 17.2 硬约束条目不会被本条款反转。

## 条款 2 · critical 最低召回深度 L3+L4+L2（P2-9-②）

### 2.1 规格依据
- `需求规格书.md:353`：critical scene 禁用极简（合规场景最低召回深度 L3+L4+L2 占位符，见 16.5）。
- `需求规格书.md:3155`（16.5 表第 7 行）：同上，明确「占位符」。
- `recallModes.ts:106`：`COMMON_INVARIANTS` 中同样标注「占位符」。

### 2.2 语义定义（已批准 · 2026-11-25，正文已去掉「占位符」，改为裁剪下限守卫）
1. **触发条件**：`normalizeScene(scene) === 'critical'`（与 16.5 同口径；手动极简已被降为 fact_first）。
2. **最低深度含义**：最终注入集在预算允许范围内，**至少**包含 L3、L4、L2 各 1 条（若该层无候选，按「证据不足如实返回」标注缺失，不编造）；预算不足以容纳三层时，按 `budget.status` 硬熔断处理，**不伪造占位内容**。
3. **层级角色**：按 `fact_first` 模式 `selectPriority = ['L3','L4','L2','L5']` 的角色——L3 真实事实为准、L4/L2 作参考/注脚；不得因最低深度要求把低分条目强行置顶到 winner 位。
4. **与裁剪顺序的关系**：`critical` 场景下 `trimOrder = ['L5','L2','L4','L3']` 不变；最低深度是**裁剪下限守卫**——裁剪后若某层归零且该层原本有候选，拒绝该次裁剪并回退到上一层预算档（如实标注 `depth_guard=triggered`），不静默丢层。

### 2.3 接线点（拟）
- `src/core/memagent/agent.ts`：预算裁剪函数后新增 `assertMinDepth(hits, scene, mode)` 守卫；触发时写审计 `action=depth_guard`。
- 回显：`evidence_thin` 与 `depth_guard` 并列为可观测告警，不新增用户可见控件。

### 2.4 验收判据
- critical 场景下三层各有候选时，注入集含三层；某层无候选时如实标注、不编造。
- 预算不足触发守卫时审计有 `depth_guard` 记录，且不伪造占位条目。
- 非 critical 场景不受守卫影响（零打红）。

## 条款 3 · 7.2 热更词表与 config 接线（P2-9-③）

### 3.1 规格依据
- `需求规格书.md:271`：`mode_weights` 可热更新；7.2 自生长引擎每周回归调权重、调参记录进审计。
- `需求规格书.md:355/376/378`：模式特征词表 YAML 可热更新、命中阈值 `hit_threshold=2` 可配；误分流反馈闭环每周重拟词表权重。
- `召回模式设计与实现方案.md:47/53`：`resolveMode(input)` 已声明 `config?` 入参，但生产唯一调用点 `agent.ts:207` 不传。
- `recallModes.ts:111-120`：`ModeDispatchConfig { minLenZh, minLenEn, hitThreshold }` 已定义，`DEFAULT_DISPATCH_CONFIG` 为基线。

### 3.2 语义定义（已批准 · 2026-11-25）
1. **热更对象**：`MODE_FEATURE_WORDS`（词表）、`ModeDispatchConfig`（阈值）、五模式 `mode_weights`——三项均由本机账本 `growth:v1` 快照承载，7.2 每周回归产出新值写快照，召回时读取快照覆盖内核 const 基线。
2. **回退语义**：快照缺失/解析失败/权重和 ≠ 1.0/阈值越界 → **整块回退内核基线**（与 `growthConfig.ts` 既有「权重和 ≠ 1 → 整块回退默认」同口径），不按比例偷偷修正、不静默用部分值。
3. **config 接线**：`resolveMode({ ..., config })` 的 `config` 由召回入口从 `growth:v1` 快照派生（含词表/阈值/权重）；生产不再省略。测试可显式传 config 覆盖，验证热更生效与回退。
4. **审计**：每次热更生效写 `action=weight_tuned` 或 `action=dispatch_config_applied`，记录 `source=growth:v1` 与旧→新值；回退写 `action=dispatch_config_fallback` + 原因（与 `growthConfig.ts` 的 `denied` 原因表同源，不写第二套）。

### 3.3 接线点（拟）
- `src/core/memagent/agent.ts:207`：生产调用补 `config`（从 `growth:v1` 快照派生）。
- `src/shared/growthConfig.ts`：扩展快照 schema 容纳词表/阈值（权重已有）；复用既有校验函数，不新立校验。
- 权重热更遵守 P1-6 口径：和为 1.0，骨架层不换。

### 3.4 验收判据
- 快照有效时热更生效（词表/阈值/权重各一例），审计有对应 action。
- 快照异常（权重和 ≠ 1 / 阈值越界 / 解析失败）整块回退基线，审计有 `dispatch_config_fallback`。
- 生产调用不再省略 config；`resolveMode` 纯函数契约不变（仍不读存储，config 由调用方注入）。
