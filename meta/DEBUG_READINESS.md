# BUG 可定位性 · 事前准备（让 BUG 自动指向问题程序段）

> 目标：在写代码时就埋好"定位线索"，将来 BUG 出现时能秒级定位到模块 / 函数 / 段落，而不是全项目地毯式搜索。
> 配套：编码执行见 [`meta/CODING_SOP.md`](meta/CODING_SOP.md)；可追溯映射见 [`specs/code-map.md`](specs/code-map.md)。

---

## 一、可追溯性（代码 ↔ 需求 ↔ 测试）
- 每段逻辑标注它服务哪个 REQ / TC，如注释 `// REQ-001 / TC-001`。
- 维护 **code-map**：`specs/code-map.md` 记录 `REQ → 模块 → 文件 → 函数 → 测试`。
- 效果：测试 `TC-007` 失败 → 查 map → 直抵 `src/services/register.ts:42`，无需搜索。

## 二、模块化与边界（来自原子任务）
- 每个任务边界清晰 → BUG 被锁在单模块内（[`meta/CODING_SOP.md`](meta/CODING_SOP.md) 已约束）。
- 单一职责：一个函数只做一件事，命名即语义（`RegisterService.create`），靠名字就能找到文件。

## 三、结构化日志与错误（可观测性）
- 统一日志：每条带 `module`、`traceId`（追踪ID）、`userId`、时间戳、级别。
- 错误不吞：抛出带 `code` + 现场上下文的 typed error，含 `file:line`。
- 关键路径埋点（请求入口 / 出口、外部调用），出错即知落在哪一段。

## 四、测试即定位器
- TDD：每个函数有单测 → 哪个 `TC` 红就知道哪段坏。
- 集成 / E2E 红 → 缩小到模块边界，再下钻到函数。

## 五、版本与变更线索
- 每个 commit message 含 `T{n}` 与 `REQ`：便于 `git blame` 回溯"这段为何这样写"。
- 分支 / PR 关联任务，变更有迹可循。

## 六、类型与契约
- 静态类型 + schema：编译期拦掉一类 BUG，且类型即文档。
- 模块接口契约固定，破坏契约的改动立刻被测试抓到。

## 七、运行期线索
- 全局错误处理器记录 stack + 上下文。
- 监控 / 告警按模块维度：哪个模块报错率升高立刻知道。

## 八、知识沉淀
- `known-issues.md`：已知故障模式 → 模块 / 段落映射。
- runbook：常见症状 → 排查路径。

---

## 九、检查清单（编码前 / 中必做）
- [ ] 函数 / 模块标注服务的 REQ / TC
- [ ] code-map 已更新
- [ ] 错误带 `code` + 现场上下文，不吞
- [ ] 关键路径有结构化日志
- [ ] 单测覆盖（TDD）
- [ ] commit message 含 `T{n}` / `REQ`
- [ ] 不整体重写，保持段落小而可定位

---

## 与 BUG 处理 SOP 的关系
- 本文件 = **事前准备**（让 BUG 可定位）。
- 后续 BUG SOP = **事中流程**（最小复现 → 定位 → 修 → 沉淀）。
- 两者结合：准备做足，事中定位从"搜全项目"变成"看一眼 map + 红测试"。
