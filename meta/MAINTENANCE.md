# 项目维护手册（操作规程）

> 回答"项目怎么维护"：谁、在什么时机、改什么、怎么保证没改坏。
> 本文件是项目的"操作 SOP"，新人/Agent 都按它来，项目就不会腐化。

---

## 一、角色与分工

| 角色 | 职责 |
|------|------|
| **人（你）** | 定方向、评审验收、合入 PR、做最终决策 |
| **Agent** | 按索引按需加载、外科手术式修改文件、跑校验、写 CHANGELOG |
| **校验脚本** `tools/validate_project.py` | 门禁：红 = 不准合入 |
| **Git** | 真相源：可 diff、可回滚、可审计 |

原则：**Agent 不拥有最终决定权，人审；但 Agent 必须保证每次改动后校验通过。**

---

## 二、每次改动的标准动作（6 步，必做）

1. **拉最小上下文**：只读 `meta/index.md` + `meta/charter.md`（常驻，约 2k token）。
2. **定位**：只打开本次相关的文件，**不要读全量**（这是省 token 的核心）。
3. **修改**：外科手术式 Edit，只动对应章节 / 段落，不整体重写。
4. **编号**：新增顺延（如 `REQ-003`）；删除必须同步清理其 AC / TC。
5. **校验**：`python tools/validate_project.py`，必须 **0 失败** 才继续。
6. **提交**：`git commit -m "REQ-003: 新增登录限流"`。

---

## 三、增 / 删 / 改 章节的具体做法

### 新增「章节」（文件内，如加一条需求）
- 在 `specs/requirements.md` 末尾加 `## REQ-003 ...`
- 同步在 `acceptance.md` / `test-plan.md` 加对应 `AC-003` / `TC-003`
- 不需要改 `index.md`（索引指向"文件"，不指向"章节"）

### 新增「一个产物文件」（如新加一个 UI 页）
- 在 `design/ui/` 下新建 `03-profile.html`
- **必须**在 `meta/index.md` 登记：`[个人页](design/ui/03-profile.html)`
- 不登记 → 校验器报"孤儿文件"告警

### 删除「章节」
- 删 `REQ-002` 时，校验器会报 `AC-002`/`TC-002` "引用断裂"
- 按提示同步删除对应 AC / TC，再跑校验至全绿

### 重命名 / 合并
- 更新所有引用（REQ/AC/TC 互指），校验器的"引用完整性"会兜底抓悬空

---

## 四、防腐化铁律

1. **索引即契约**：任何新产物文件必须登记进 `meta/index.md`。
2. **编号对应**：`REQ ↔ AC ↔ TC` 一一对应；删一个必查其余。
3. **决策留痕**：重要变更写 `meta/decisions.md`（ADR），记"为什么"，防被错误改动推翻。
4. **会话压缩**：长对话每几轮，把"已定决策 + 待办"压进 `decisions.md` / `CHANGELOG.md`，丢弃早期原文，用状态文件替代上下文。

---

## 五、周期维护

- **每日**：改完即校验 + 提交（见第二节）。
- **每周**：跑一次全量校验 → 清理孤儿 → 更新 `charter.md` / `decisions.md`。
- **里程碑**：重新生成 `build/` 产物 + 全量测试通过，再发版。

---

## 六、发现漂移 / 错误时

校验器红灯 → 看报告定位"哪个文件 / 哪个 ID" → 外科修复 → 再跑校验至绿 → 提交。
若文档与代码不一致：**以 `specs/` 为权威**——代码不符就改代码，specs 要变则走评审 + ADR。

---

## 七、常用命令

```bash
# 完整性 / 正确性门禁（每次改动后必跑）
python tools/validate_project.py

# 提交变更
git add -A && git commit -m "REQ-003: 新增登录限流"

# 看当前项目全貌（只读索引，不加载全文）
cat meta/index.md
```
